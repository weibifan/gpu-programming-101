# 00 为什么需要 GPU：从 x86 CPU 讲起

> 对应里程碑 M1。本文假定读者只熟悉 x86 电脑，从未接触线程、核心、SIMD、浮点等概念。我们从"电脑怎么算数"开始，一步一步讲清：程序如何变成 CPU 能执行的指令、CPU 内部怎么干活、为什么 CPU 不够用、GPU 凭什么快、什么任务才适合 GPU。

**阅读路线**：本文是入门的第一篇，目标是建立"计算"和"并行"的直觉。读完后你应能回答：一条指令是什么？浮点数怎么存？CPU 为什么堆不上核心？SIMD 和 SIMT 有什么关系？为什么 GPU 需要海量线程？

## 1. 程序是怎么变成机器码的：从源代码到指令

### 1.1 人类写的代码 ≠ 机器能懂的代码

你写的 `c = a + b`（高级语言，如 C/Python），CPU 根本看不懂。CPU 只认**机器码（machine code）**——一串二进制数字，如：

```
8B 45 FC     （把内存地址里存的值拷进寄存器）
03 45 F8     （两个数相加）
```

机器码是给硬件用的"最终说明书"。把高级语言变成机器码，需要经过**编译（compile）**：

```
源代码 (c = a + b)
   │ 编译器 (gcc / cl.exe / nvcc)
   ▼
汇编 (assembly)：人类可读的助记符，如 mov、add
   │ 汇编器
   ▼
机器码 (二进制)
   │
   ▼
CPU 执行
```

> 中间还有一层**汇编语言（assembly）**，用 `mov`、`add` 这类助记符代替二进制，让程序员勉强能读。今天很少有人手写汇编，但理解"高级语言一行 = 底层好几条指令"很重要——**性能优化的本质，就是让 CPU/GPU 少执行指令、少搬数据**。

Python 这种**解释型语言**则不同：不是一次性编译成机器码，而是由一个解释器（如 CPython）在运行时一句句翻译执行，天然比 C 慢。深度学习性能敏感的部分（如 PyTorch 底层）几乎全部用 C/C++ 实现，Python 只是"指挥层"。

### 1.2 一条指令长什么样

以 x86 为例，一条指令大致包含三部分信息：

| 部分 | 作用 | 例子 |
|---|---|---|
| **操作码（opcode）** | 干什么 | `ADD`（加）、`MOV`（拷贝）、`CMP`（比较） |
| **源操作数** | 从哪取数 | 寄存器 `%eax`、内存 `[地址]`、立即数 `5` |
| **目标操作数** | 结果放哪 | 寄存器 `%ebx` |

例如 `ADD %eax, %ebx` 的意思是"把寄存器 eax 的值加到 ebx 上，结果存回 ebx"。

> 这里首次出现一个关键词：**寄存器（register）**。它是 CPU 内部极少量的"速记本"，装正在运算的数。CPU 不能直接从内存里做加法——必须先 `LOAD`（内存→寄存器），算完再 `STORE`（寄存器→内存）。这种设计叫 **LOAD/STORE 架构**，几乎所有 CPU 和 GPU 都如此。

### 1.3 指令是"死的"，程序计数器是"活的"

CPU 怎么知道下一步该执行哪条指令？靠一个特殊寄存器叫 **程序计数器（PC, Program Counter）**，它记录"下一条指令在内存里的地址"。执行完一条，PC 自动加一指向下一条（`jmp`/`call` 等跳转指令可改 PC）。所以程序执行的本质是：

```
取指（按 PC 读指令）→ 译码（看懂指令）→ 执行（动手算）→ 写回（存结果）→ 更新 PC → 回到取指
```

每走完一圈叫一个**时钟周期（clock cycle）**。CPU 主频 3.5 GHz，意味着每秒走 35 亿个周期。但注意：**一条复杂指令可能要多个周期**，不是"1 主频 = 1 条指令"。

## 2. 数据在内存里怎么表示：整数与浮点数

### 2.1 一切皆二进制

计算机里没有"数字"，只有**高低电平（0 和 1）**。一个 0/1 叫 **bit（位）**，8 个 bit 叫一个 **byte（字节）**。

| 名字 | 位数 | 能表示范围（无符号） | 例子 |
|---|---|---|---|
| char / int8 | 8 | 0~255 | 一个字符 |
| int / int32 | 32 | 0~42 亿 | 常见整数 |
| long / int64 | 64 | 0~1.8×10¹⁹ | 大数 |

带符号整数用**补码（two's complement）**表示：最高位是符号位，`-1` 存成 `1111...1`。好处是加法和减法共用一套硬件——CPU 里只有加法器，减法"加个负数"就行。

### 2.2 浮点数：不是所有数都是整数

游戏分数、深度学习权重（0.3、-1.7e-5）都需要**小数**。计算机用 **IEEE 754 标准** 存浮点数，本质是科学计数法的二进制版：

```
值 = (-1)^符号 × 1.尾数 × 2^指数

float (FP32)  32 bit = 1 符号 + 8 指数 + 23 尾数
double (FP64) 64 bit = 1 符号 + 11 指数 + 52 尾数
half  (FP16)  16 bit = 1 符号 + 5 指数 + 10 尾数
```

> 直觉理解：**指数决定"量级"，尾数决定"精度"**。位越少，能表示的范围越小、精度越粗。FP16 只能精确表示约 3 位十进制有效数字，最大值只有 65504。

| 类型 | 位数 | 有效数字（约） | 最大量级 | 用途 |
|---|---|---|---|---|
| FP16 | 16 | 3 位 | 65504 | 深度学习加速（显存省一半、带宽省一半） |
| FP32 | 32 | 7 位 | 3.4×10³⁸ | 常规科学计算 |
| FP64 | 64 | 16 位 | 1.8×10³⁰⁸ | 需要极高精度的模拟 |

浮点数有几个**违背直觉**的特性，新手必踩：

- **不精确**：`0.1` 在二进制里是无限循环小数，存的是近似值。`0.1 + 0.2 ≠ 0.3`（差一点点）
- **溢出/下溢**：太大变 `inf`，太小变 `0`
- **加法顺序影响结果**：`(a+b)+c` 和 `a+(b+c)` 可能不同（舍入误差），所以并行计算时换顺序结果会有微小差异

> ⚠️ 后面讲 LLM 时你会看到：训练用 FP32 攒精度，推理常降到 FP16/int8 换速度，就是因为"精度换速度、换显存"。理解浮点表示，是理解量化的前提。

### 2.3 混合精度：低精度算、高精度攒

前面说"训练用 FP32 攒精度，推理常降到 FP16 换速度"——这句话背后就是**混合精度（mixed precision）**。先纠正一个常见误解：

> ⚠️ **混合精度不是 PyTorch 的概念，而是 GPU 硬件 + CUDA 层面的能力**。PyTorch 的 AMP（自动混合精度）只是把这种能力**自动化**的工具（详见 `04_pytorch_gpu.md` §4）。本节讲的是能力本身。

**为什么需要它**（痛点来自 §2.2 的浮点表示）：

| 痛点 | 说明 |
|---|---|
| 显存不够 | FP32 一个数 4 字节，大模型存不下；FP16/BF16 只要 2 字节 |
| 算力不够 | 低精度的 GPU 算力约为 FP32 的 2 倍；Tensor Core 更不止于此 |
| 低精度有毛病 | FP16 尾数 10 位，小值（如梯度 <1e-7）被截断成 0；指数 5 位，最大 65504，稍大就变 inf |

**BF16 是哪来的？** 刚提到的 FP16 有个致命短板：**动态范围太小**（指数只有 5 位，最大 65504），训练时权重/梯度稍大就变 `inf`。Google Brain 于是设计了一个"半精度"的第二个方案，取名 **BF16 = bfloat16 = Brain Floating Point（脑浮点）**：

> 注意：IEEE 754 标准正式收编的半精度只有 **FP16（binary16）**；**BF16 不在 IEEE 754 之列**，是 Google 提出后被 Arm 固化为规范、Intel/AMD/NVIDIA 广泛采纳的**事实标准**——你见到的"BF16 支持"都是厂商按惯例实现的。

```
FP32：1 符号 + 8 指数 + 23 尾数
FP16：1 符号 + 5 指数 + 10 尾数   ← 另起炉灶，范围和精度都牺牲
BF16：1 符号 + 8 指数 + 7  尾数   ← 直接砍 FP32：指数位原封不动，只扔 16 位尾数
```

BF16 的做法是把 FP32 **截断成 16 位**：尾数砍到只剩 7 位，但**指数位完整保留 FP32 的 8 位**——所以它的**动态范围和 FP32 一模一样**，永远不会像 FP16 那样溢出，代价只是有效数字更少（约 3 位）。深度学习的实践发现：出问题往往是因为**范围不够（溢出）**，而不是精度不够，所以 BF16"够粗但绝不爆"，成了 Ampere 起 Tensor Core 的默认选择。一句话记忆：**FP16 是"重定规则"，BF16 是"只砍精度、保住范围"**。

**还有第三种：TF32（Tensor Float 32）——不换 dtype 的"缩水版 FP32"**

```
FP32：1 符号 + 8 指数 + 23 尾数
TF32：1 符号 + 8 指数 + 10 尾数   ← 指数原封不动，尾数砍到 10 位（共 19 位）
```

TF32 是 **Ampere 架构起 Tensor Core 的专用输入格式**（A100、RTX 30/40/50 系列，计算能力 ≥ 8.0；V100 及更早没有）：指数位和 FP32 完全一样（8 位，动态范围不变、不会溢出），只把尾数从 23 位砍到 10 位。它和 FP16/BF16 的关键区别——**TF32 不是存储格式**：显存里仍是 FP32（**不省显存、不省带宽**），只是矩阵乘**喂进 Tensor Core 那一刻**把尾数裁成 10 位来算。所以：

- **和 FP16/BF16 的关系**：FP16/BF16 换 dtype、省一半显存/带宽；TF32 **不换 dtype**、不省显存，纯粹让 **FP32 矩阵乘**也在 Tensor Core 上跑（约 2 倍于纯 FP32），代价是尾数精度略降
- **在 PyTorch 里的开关**：`torch.set_float32_matmul_precision('high')`（用法见 `04_pytorch_gpu.md` §4.1）

一句话记忆：**FP16 重定规则、BF16 保范围砍精度、TF32 是"FP32 自己进 Tensor Core 前临时缩一下水"**。

**混合精度怎么做**：不是全盘降精度，而是**分类对待**——

* 精度敏感的部分保持 FP32：损失计算、LayerNorm / softmax、优化器累加
* 精度不敏感的部分用 FP16/BF16：矩阵乘法、卷积、注意力投影

关键在**硬件支持**：GPU 的 **Tensor Core**（§10.5 的"九九表机"）天生就是为混合精度设计的——**输入是 FP16/BF16（省内存、省带宽），乘加累加却用 FP32（不丢精度）**。这正是"用低精度算、用高精度攒"的硬件版本。

**三层分工（能力 vs 工具）**：

| 层 | 干什么 |
|---|---|
| GPU 硬件（Tensor Core） | 提供"低精度输入 + FP32 累加"的算力——**能力的源头** |
| CUDA 库（cuBLAS / cuDNN） | 实现低精度 kernel（如 `cublasGemmEx` 指定计算精度），把硬件能力暴露出来 |
| PyTorch AMP | 自动化调度：`torch.amp.autocast` 帮你决定哪些算子该用低精度——**不提供能力，只负责用** |

> 底层收益链：FP16 省一半字节 = **省一半带宽 = 吞吐翻倍**（对应 §11 的 memory-bound 直觉）；Tensor Core 又带来数倍于 FP32 的算力。二者叠加，就是 LLM 训练/推理里"又快、又省、又不太掉精度"的秘诀。量化（`05_llm_acceleration.md` §4）是同一思路的再进一步。

## 3. 存储层级：为什么 CPU 要缓存

### 3.1 主存太慢了

CPU 从主存（RAM）读一个数可能要等 **200+ 个周期**，而一次加法只要 1 个周期。如果不做任何处理，CPU 大部分时间都在"干等数据"。所以 CPU 芯片上塞了多级**缓存（cache）**：

| 存储 | 位置 | 延迟（约） | 容量 | 特点 |
|---|---|---|---|---|
| 寄存器 | 核心内部 | 1 周期 | 几十个 | 装正在算的数，靠名字访问 |
| L1 缓存 | 核心内部 | ~4 周期 | 32~64 KB | 最近用过的指令/数据（分 L1i 指令 + L1d 数据） |
| L2 缓存 | 芯片上 | ~12 周期 | 几百 KB~几 MB | 稍大一点的缓存 |
| L3 缓存 | 芯片上（多核共享） | ~40 周期 | 几 MB~几十 MB | 核间共享 |
| 主存（RAM） | CPU 外 | 200+ 周期 | 几 GB~几十 GB | 程序和数据的家 |
| 磁盘/SSD | 机箱内 | 百万+ 周期 | 几百 GB~TB | 关机不丢数据 |

规律：**越靠近 CPU 越快、越小、越贵**。缓存存在的唯一理由：靠**局部性原理**用很少的容量命中大部分访问。

> 注意 L1 缓存实际分两条：**L1i（指令缓存）**缓存"取指"阶段读到的指令，**L1d（数据缓存）**缓存 LOAD/STORE 阶段搬的数据。CPU 的取指路径和存取数据路径各走各的缓存、互不挤占——正好呼应第 1.3 节的"取指→执行"回路和第 1.2 节的 LOAD/STORE 架构，两条路各自有缓存加速。

### 3.2 缓存行与局部性

缓存不是按字节存的，而是按 **cache line（缓存行）** 成块搬运（x86 上典型 64 字节 = 16 个 float）。访问 `arr[0]` 时，`arr[0]~arr[15]` 一起被搬进缓存——这叫**空间局部性**：相邻数据大概率会被一起用。连续访问数组就是最好的空间局部性。

另一个是**时间局部性**：刚用过的数据很快还会用（比如循环变量）。程序性能差异常常不在于算法本身，而在于**缓存命中率**。后面 CUDA 优化里反复强调"**合并访问（coalesced access）**"就是在 GPU 上复用"按行连续搬"这个道理。

> 关键直觉：**CPU 从主存读一个数，可能要等几百个周期**。所以 CPU 里塞满了缓存和各种"预测"技术来减少等待；GPU 走的却是另一条路（海量线程藏延迟），见第 7 节。

## 4. CPU 内部怎么让单核变快：四大招

一个 CPU 核心是一整套"取指→执行"硬件。为了让单核变快，芯片工程师用了四招，理解了它们，你就懂了为什么 CPU 核心"又大又重"。

### 4.1 流水线：让各阶段错开，而不是等完一个再下一个

假设一条指令要 5 个阶段、每阶段 1 周期。不用流水线，一条指令 5 周期，只能 1/5 的效率。流水线让第 1 条指令执行时，第 2 条已经取指……像工厂流水线，各工位同时忙：

```
时间 →  1    2    3    4    5    6    7    8
指令1  取指 译码 执行 访存 写回
指令2       取指 译码 执行 访存 写回
指令3            取指 译码 执行 访存 写回
指令4                 取指 译码 执行 访存 写回   ← 每周期完成 1 条
```

理论上 5 级流水线把吞吐提高到 5 倍。但**流水线怕"中断"**：遇到跳转（if/循环）、数据依赖，后段要清空重来（叫 **pipeline stall**）。于是有了第 2、3 招。

### 4.2 超标量与乱序执行：一个周期干好几条

现代 x86 核心有多个执行单元（ALU 做算术、Load/Store 单元、FPU 做浮点），可以**一个周期发射多条无关指令**，这叫**超标量（superscalar）**。如果指令之间有依赖，处理器会**乱序执行（Out-of-Order）**——把后面的独立指令提到前面先做，不影响结果。

### 4.3 分支预测：猜对了就省事

`if (x > 0) ...` 这种跳转会打断流水线。CPU 用**分支预测器**猜结果：猜对了，流水线不中断；猜错了，白干一截还得回滚。猜得准不准（特别是循环方向），直接影响性能。

### 4.4 超线程：一个核心当两个用

一个核心内部总有闲置单元（访存时 ALU 闲着）。**超线程（Hyper-Threading）**让一个物理核心维护 2 套执行上下文，错峰填满空闲单元。所以"8 核 16 线程"= 8 个物理核心 + 超线程 = 16 个**硬件线程**。

> **小结**：这四招的目标都是"把单核的空闲时间填满"。代价是核心内部极其复杂——几百万个晶体管做预测器、乱序引擎、大缓存。这就解释了后面 GPU 为什么要"反着来"。

## 5. 单核碰壁：功耗墙与多核时代

### 5.1 频率为什么上不去了

CPU 频率从 1990 年代几百 MHz 涨到约 4~5 GHz 后**停滞了**。物理原因：

- **功耗墙**：芯片功耗近似 `P ≈ C·V²·f`（C 电容、V 电压、f 频率）。想提频率就得提电压，功耗按平方涨；真实约束下频率每翻一倍，功耗涨约 8 倍
- **散热**：一颗 CPU 功耗几十~上百瓦，热量集中在指甲盖大小的芯片上，散热已压不住
- **量子效应**：晶体管越来越薄，电压稍高就漏电，频率稍快就信号错乱

> **摩尔定律的转折**：晶体管数目还在按"摩尔定律"翻倍，但**单核频率不再能翻倍**。芯片厂商于是转向：晶体管多了，不去做更快的单核，而是塞更多核心——**用并行换速度**。

### 5.2 多核 CPU：请几个工人，而不是一个超人

**核心（core）= 一套独立的取指→执行硬件**（含自己的寄存器、L1/L2、流水线）。多核 CPU 就像请了几个工人：

```
┌────────────── CPU ──────────────┐
│  核心0   核心1   核心2   核心3   │  4 核可同时算 4 份
│  └各带自己的 L1/L2 + 流水线┘    │
│         L3 缓存（共享）          │
└─────────────────────────────────┘
```

一个 8 核 CPU 理论上可以同时做 8 件事。但注意两个现实：

- **不是 8 核就快 8 倍**：前提是任务能拆成 8 份互不干扰的小块；串行部分（拆解、汇总、核间通信）拖后腿，见 Amdahl 定律（第 9.4 节）
- **核间通信有成本**：核心要共享数据，得通过 L3 缓存/总线，还要维护**缓存一致性**（一个核改了数据，其他核的缓存副本必须失效，否则读到旧值）——锁、原子操作、内存屏障都为此服务

### 5.3 桌面 CPU 的极限

| 局限 | 说明 |
|---|---|
| 核太少 | 台式机最多 8~64 个物理核心 |
| 每核太重 | 单线程性能优先，塞满乱序执行、分支预测、大缓存 |
| 线程切换有成本 | 操作系统切换线程要保存/恢复上下文（微秒级） |
| 内存带宽有限 | 多核共享内存带宽，典型 x86 台式机约 50 GB/s |

一句话：**CPU 能真正同时运行的硬件线程"又大又少"**。

## 6. 什么是线程：CPU 视角

### 6.1 从"进程"到"线程"

你打开的程序（浏览器、Word）叫**进程**，它占有独立的虚拟内存空间。进程内可以再拆成多条**线程（thread）**：

- **线程 = 进程内一条独立的执行流**（有自己的一组寄存器、栈、程序计数器，但共享进程的内存）
- 单核时靠"快速轮换"看起来同时跑，叫**并发（concurrency）**
- 多核时不同线程真正同时跑在不同核心上，叫**并行（parallelism）**

> 并发是"轮流干"，并行是"同时干"。这是两个容易被混淆的概念。

### 6.2 OS 线程 ≠ 硬件线程

| | 操作系统线程（OS 线程） | 硬件线程（hardware thread） |
|---|---|---|
| 本质 | **软件概念**：进程内执行流 + 上下文 | **硬件概念**：物理核心能同时维护的执行状态 |
| 谁在管 | 操作系统调度器 | CPU 硬件 |
| 数量 | 随便建，成千上万 | 极少，如 8 核 16 线程 = 16 个 |
| 类比 | "待办任务" | "工位" |

关系一句话：**操作系统把 OS 线程调度到硬件线程（工位）上执行**——一个工位同一时刻只坐一个待办任务。你创建成千上万个 OS 线程没问题，但同一时刻只有被调度到那 16 个硬件线程上的在真正运行，其余都在排队。

## 7. CPU 的隐藏武器：SIMD——理解 GPU 的桥

### 7.1 一条指令处理多个数据

你可能不知道：你的 x86 CPU **早就支持"一条指令算一堆数"**了。这就是 **SIMD（Single Instruction, MultiSIMD类似于矩阵运算，也就是从值加法，变成了矩阵加法。ple Data，单指令多数据）**，通过指令集扩展实现：

| 扩展 | 寄存器宽度 | 一条指令同时算 | 年代 |
|---|---|---|---|
| MMX | 64 bit | 2 个 float | 1997 |
| SSE | 128 bit | 4 个 float | 1999 |
| AVX | 256 bit | 8 个 float | 2011 |
| AVX-512 | 512 bit | 16 个 float | 2017 |

例如一条 `vaddps`（AVX 加浮点向量指令）可以一口气把 8 个 float 两两相加。效果：

```
CPU 传统方式：  a0+a1  再 a2+a3  再 a4+a5 ...   （8 条指令）
CPU 用 AVX：    [a0..a7] + [b0..b7]  →  8 个和   （1 条指令）
```

**这正是 GPU 设计思想的 CPU 雏形**：与其一条指令算一个数，不如一条指令算一堆数。区别只在于规模：CPU 的 SIMD 是"一个核心内部，宽度 256 bit、算 8 个 float"，GPU 则把这个思想放大到"成百上千个核心 × 每条指令算 32 个数"。

### 7.2 为什么编译器和程序员都在意 SIMD

- 编译器会自动把 `for (i...) a[i]=b[i]+c[i]` 这样的循环**向量化**成 SIMD 指令（前提：没有依赖、内存连续）
- 写高性能代码时，让数据在内存里**连续摆放、按对齐访问**，编译器才能向量化——这个思维会一路带到 CUDA 里（合并访问、向量化 load）

> **记住这张桥**：CPU 有 SIMD（一个核、窄宽度），GPU 有 **SIMT（Single Instruction, Multiple Threads，单指令多线程，详见 §10.2）**（许多核、宽并发）。下文 GPU 的 warp、线程概念，本质是"把 SIMD 的规模放大到极致"。

## 8. 并行的思路：任务拆解

假设有 100 万个数字，每个要 +1。串行做法是一个一个算，并行做法是：

```
把 100 万个数分成 1 万个块，每块 100 个数
→ 让 1 万个"工人"每人负责一块，同时动手
→ 理论上快了 1 万倍
```

这种"把数据切成很多份、每份交给一个工人"的模式叫**数据并行（data parallelism）**，是 GPU 最擅长的。相对的有**任务并行**（不同工人干不同的事，如流水线各阶段）。

## 9. GPU 的答案：把"工人"数量堆到极致

### 9.1 反过来设计：放弃单核复杂度，堆海量简单核心

既然 CPU 单核被功耗墙锁死、核数又上不去，GPU 干脆**完全放弃"单个人跑得快"**，把资源全部砸向"人数"：

- CPU：几千人里挑 8~64 个"全能冠军"（复杂核心、低延迟、赌局部性）
- GPU：直接雇几千个"只会做重复简单活"的工人（轻量核心、高吞吐、赌并行度）

这是两种设计哲学：**CPU 优化延迟（latency）**——一件事尽快做完；**GPU 优化吞吐（throughput）**——单位时间做更多事。

### 9.2 GPU 的"线程"轻到离谱

GPU 线程和 CPU 硬件线程有本质区别：

| | CPU（硬件线程） | GPU 线程 |
|---|---|---|
| 数量 | 几十个（逻辑处理器） | 几万~几十万个 |
| 单个成本 | 高（完整上下文+调度） | 极低（仅一组寄存器） |
| 创建/切换开销 | 微秒级 | 几乎为零，硬件直接换 |
| 擅长的活 | 任意复杂逻辑 | 大量重复的简单运算 |

> GPU 线程**既不是 OS 线程**（无需操作系统参与创建调度），**也不是 CPU 硬件线程**。它就是"一组寄存器 + 执行状态"构成的极轻量执行上下文，由 GPU 硬件调度器直接管理，可同时驻留成千上万个。

### 9.3 延迟隐藏：GPU 不用缓存，改用"人手"

CPU 靠 L1/L2/L3 缓存 + 分支预测把内存延迟藏起来；GPU 内存延迟更高（几百周期），但它**不靠缓存，靠线程数量**：

```
一个线程等内存（几百周期，闲着）
   ↓ 硬件调度器瞬间切换
另一个线程开始算（这段时间有别的线程在算）
```

这叫**延迟隐藏（latency hiding）**。一个 **SM（流式多处理器，GPU 上的计算单元，相当于一个"小团队"，详见 §10.1）**上驻留几千个线程，每个线程等数据时调度器立刻换下一个线程干活，时间从不浪费。**线程越多，越能藏住延迟**——这就是 GPU 需要海量线程的根本原因，也是为什么"给 GPU 的线程数太少反而跑不快"。

### 9.4 并行不是免费的：Amdahl 定律

$$加速比 = \frac{1}{(1 - P) + P/N}$$

- `P` = 可并行比例，`N` = 工人数
- 即使工人无限多，加速比也封顶在 `1/(1-P)`
- **教训：串行部分才是瓶颈**。GPU 算得快之后，真正慢的往往是数据加载、内存拷贝、CPU 预处理——这就是为什么优化要"先解决搬数据，再解决算得快"。

## 10. GPU 硬件长什么样

### 10.1 从外到内：三层结构

```
GPU 显卡
└── SM（流式多处理器）— 内部核心计算单元，相当于一个"小团队"
    ├── CUDA Core × N     — 轻量算数单元（ALU），类似 CPU 核心但弱得多、多得多
    ├── 共享内存          — 团队（block）内部的"微信群"（见 §10.4 例子）
    ├── 寄存器堆          — 给每个线程分"口袋"
    └── warp 调度器       — 负责切换执行哪个 warp（线程束，见 10.2）
```

- **第一次见"CUDA Core"，先认清名字**：它是**硬件概念**——SM 里一个实实在在的 **FP32 算术单元（ALU）**（顺带做整型运算），本质就是"一个能算数的算术单元"。名字里的 **CUDA 只是 NVIDIA 软件栈的商标标签**，与硬件本质无关：同一块芯片改用 OpenCL、HIP 等语言编程，跑的还是这些物理 ALU，只是不叫 CUDA Core
- **它不是 CPU 意义上的"核心"**：没有取指/译码/调度能力，寄存器来自 SM 的寄存器堆，只负责"拿到操作数就算"（对应 §10.4 比喻里的**算盘**）。把"2560 个 CUDA Core"和"8 核 CPU"直接比大小是错误直觉
- 一块 GPU 有多张 **SM**（GTX 1080 有 20 个，A100 有 108 个）

### 10.2 SIMT：GPU 版的 SIMD，一条指令、32 个线程

GPU 的并行模型叫 **SIMT（Single Instruction, Multiple Threads，单指令多线程）**：

- **一条指令**被**多个线程**同时执行
- 每个线程操作**自己的数据**（各自寄存器里那份）

GPU 实际调度单位是 **warp（线程束）= 32 个线程**。一个 warp 内 32 个线程**必须同时执行同一条指令**，这和我们 CPU 的 AVX "一条指令算 8 个数"本质同构，只是：

| | CPU SIMD（AVX） | GPU SIMT（warp） |
|---|---|---|
| 宽度 | 8 个 float | 32 个线程 |
| 数据来源 | 固定的 8 个寄存器位置 | 每个线程自己的寄存器 |
| 分支 | 无（硬件向量指令） | 可有（但会发散，见下） |
| 数量 | 每核 1 组 | 每个 SM 几万个线程/几十个 warp |

若 warp 内有人走了不同分支，就得"分叉"后串行执行——这叫 **warp 发散（warp divergence）**，是后面优化章节的重点。

```
一条指令"x = x + 1"
同时作用于 32 个线程：
  ┌────┬────┬────┬────┬────┐
  │ t0 │ t1 │ t2 │ ...│ t31│  每个线程给自己的 x 加 1
  └────┴────┴────┴────┴────┘
```

### 10.3 GPU 编程的三层抽象：thread、block、grid（x86 上没有的概念）

三层结构是 GPU 独有的编程抽象，**x86 CPU 编程里根本没有**——CPU 只有"操作系统线程"一个层次，由操作系统调度；GPU 则把线程组织成固定层级，交给硬件自己调度。看懂这三层，就读懂了一半 CUDA 代码（详见 `02_cuda_basics.md`）：

```
grid（网格，一次 kernel 启动 = 一个任务）
└── block（线程块）── 整个指派给某个 SM 执行
    └── thread（线程）── 最小执行单元，最底层写的"代码"
```

**为什么中间要夹一层 block？** 两个理由：

- **为了协作**：同一个 block 内的线程能**同步**（`__syncthreads()`）、能共享一块**共享内存**（block 内部共用的"微信群"，见 §10.4 例子），可以互相传数据、分工干活——比如矩阵乘分块时，一个 block 负责算一块结果，块内线程共享那一块数据
- **为了扩容**：不同 block 之间**完全独立、无法同步**，所以想启动多少个 block 就能启动多少——每个 SM 可以同时驻留**多个** block（上限受每 SM 的线程/寄存器/共享内存额度限制），所以全卡同时跑的 block 数 = SM 数 × 每 SM 驻留数，超出的 block 在 GPU 内排队等待。任务规模因此可以无限放大，这是 CPU 做不到的。具体"装箱"过程见下方"10.1 和 10.3 的关系"

**三层抽象和硬件的关系**：

| 抽象 | 对应硬件 | 作用 |
|---|---|---|
| grid | 一次 kernel 启动 | 描述"整个任务有多大" |
| block | 一个 SM | 协作单位：可同步、可共享内存 |
| thread | 一个轻量执行上下文（见 §9.2） | 最小执行单元 |
| warp（见 §10.2） | 硬件调度粒度 | block 会被 SM 自动切成若干个 warp（32 线程）逐一调度 |

**10.1 的硬件结构和 10.3 的抽象是一一对应的**：10.1"从外到内"是**硬件**的嵌套（显卡 → SM → 内部组件），10.3"从大到小"是**软件抽象**的嵌套（grid → block → thread）。两层不是各说各的，而是同一件事的"你怎么描述"和"硬件怎么执行"：

```
软件抽象（10.3 你写的代码）           硬件（10.1 实际在跑的东西）
grid  ←→ 一次 kernel 启动（整个任务）  ←→ 整块 GPU 显卡（多张 SM 分工）
block ←→ 任务里的一块，整块指派给一个 SM ←→ SM（一块 block 驻留的地方）
             └ 一个 SM 可同时驻留多个 block（上限看每 SM 的线程/寄存器/共享内存额度）
thread←→ 任务里的最小执行单位：你写的代码  ←→ warp（32 个 thread 打包）
                    → warp 调度器（选哪个 warp 执行）→ CUDA Core（真正算的 ALU）
```

关键差异一句话：**软件单位是"逻辑容器"，硬件单位是"物理执行资源"**。从 block 到真正执行，硬件自动走三步，10.1 的四个组件正好各司其职：

1. **装箱（block → SM）**：显卡把 grid 里的 block 逐个派发到有空位的 SM 上驻留。block 与 SM 是"指派"关系而非 1:1——block 上报自己的线程数、共享内存需求，硬件按每 SM 的额度决定同时堆几个（这就是第 10.3 节"为什么 block 能无限多"的硬件根因）
2. **切 warp（thread → warp）**：SM 把驻留在自己上的每个 block 自动切成 32 线程一组的 **warp**（block 线程数不是 32 的倍数时，最后一个 warp 不满）；每个 thread 的"口袋"——寄存器——从 SM 的**寄存器堆**里分配
3. **调度执行（warp → CUDA Core）**：**warp 调度器**决定下一个执行哪个 warp，一条指令驱动该 warp 的全部 32 个线程在 SM 的 **CUDA Core** 上同时算（SIMT，见 §10.2）。而 10.1 的**共享内存**，正是给同一个 block 内协作的线程用的（对应 §10.3"为了协作"）

### 10.4 一个例子：学院上课——把两套三层串一遍

**用一个"学院上课"的例子把两套三层串一遍**（举具体数字）：

> 场景：一所法学院要上一堂刑法课。**学院 = grid**（一次 kernel），**系 = block**，**学生 = thread**。硬件是旁边一栋**教学楼 = GPU**，**每层楼 = 一个 SM**。每层有 **4 间教室 + 1 间休息室**：每间教室 = **32 个座位 = 32 个 CUDA Core**，配 **1 位管理员**；学生按 **32 人一班（warp）** 听课——一个班正好坐满一间教室；**休息室**最多容纳 **2048 名学生待命**（**线程驻留**：登记入住、分到了寄存器和被点名的资格，但还没在算）。**课程 PPT = 程序员写好的 kernel 代码**——全楼只此一份、开课团队提前做好，每间教室放的都是同一份，它只负责被"放"、不负责"讲"。**管理员 = warp 调度器**——每间教室一位，负责两件事：**决定哪个班进教室**（选哪个 warp 上座，即 warp 调度），以及**把当前那一页 PPT（那条指令）投给全班的 32 个学生**（**SIMT**：一条指令驱动 32 个线程）。每层 4 位管理员（**Pascal SM 正好 4 个 warp 调度器**）可同时对 4 个班上课；休息室里的其他班听不见、只能等。

设定数值：

```
抽象层（排课表上写的）
  学院（grid）= 这次刑法课，5 个系共 540 人：
  系一 200 人｜系二 150 人｜系三 90 人｜系四 60 人｜系五 40 人   ← 5 个 block，大小不一
  540 人按 32 人一班 → 共 19 个班（warp）

硬件层（教学楼）
  教学楼（GPU）= 3 层楼 = 3 个 SM
  每层 4 间教室，每间 32 个座位（= 32 个 CUDA Core）→ 每层 128 个座位
  每层 1 间休息室，最多容纳 2048 名学生待命（线程驻留）
  全校 12 间教室共 384 个座位，待命位 6144 个
```

排课（硬件自动做的"装箱"）：

| 楼层（SM） | 上课的系（block） | 怎么安排 |
|---|---|---|
| 1 层 | 系一 200 人（1 个 block） | 200 人 = 6 个满班 + 1 个 20 人班 = 7 个 warp；休息室待命，一轮最多 4 个班同时坐进 4 间教室 |
| 2 层 | 系二 150 + 系四 60（2 个 block） | 两系共 210 人 = 7 个班（5+2），同挤这一层休息室，共用 4 间教室 |
| 3 层 | 系三 90 + 系五 40（2 个 block） | 130 人 = 5 个班（3+2），最后两个班分别 26 人、8 人 |
| 全校 | 5 个 block 同时驻留 | 540 人 ≪ 全校 6144 个待命位，全装得下；同时最多 12 个班（384 人）在各教室动笔 |

对应关系逐条看：

- **block = 系，整个系打包去某一层上课，绝不拆到两层**——block 整体指派给一个 SM。为什么？因为同一个系的学生要共用这一个"微信群"互传数据（**共享内存**）、要等全班齐了再对答案（**`__syncthreads()` 同步**），拆到两层就做不到了
- **一个 SM 可以同时驻留多个 block**：2 层休息室里同时候着系二和系四。但它们互不商量（block 之间**不能同步、不能共享内存**），只是恰好共用这一层的座位和休息室资源
- **warp = 班，thread = 学生，教室 = 一个 warp 的工位**：学生被硬件自动按 **32 人一班（warp）** 分好，恰好一间教室 32 个座位、一个班坐满一间教室（**SIMT：一条指令驱动 32 个线程**）。一层 4 间教室、每间 1 位**管理员**，可同时对 4 个班上课（**Pascal SM 里正好 4 个 warp 调度器**）。让哪个班进哪间教室、谁先上座，全由管理员自动安排，学生自己不用管也管不了
- **一份 PPT、无数间教室**：**PPT（kernel 代码）全楼只有一份**，由开课团队提前写好，谁都不能现场改；管理员不备课、不创作，只负责把它翻给进来的班看。所以"一段 kernel 代码干 100 万次活"的真相是：**只有一份 PPT，管理员们把它一页页放给成千上万个不同的班（warp）看**——每个班看到的是同一份内容，只是各自进度（翻到哪一页）不同
- **教室 = 32 个座位 + 一位管理员**：每个座位有一把算盘，用于计算——下一个人来了，用同一把算盘重新算自己的东西。上课流程：**点名 → 整班走进一间教室、坐满 32 个座位（一个 warp 执行占 32 个 CUDA Core）→ 管理员把本班当前那一页 PPT（那条指令）投出来、全班低头算 → 算到要访存（查微信群消息＝**共享内存**，或跑图书馆借书＝**显存**）就得起身回休息室，管理员接着叫下一个班进来（warp 切换）**。每层 4 间教室 = 同时最多 4 个班在动笔。**这就是延迟隐藏**：休息室里候场的班够多，一有人起身立刻有下一班补进空教室，教室从不空着、楼里永远有人在算
- **算盘 = CUDA Core（ALU），笔记本 = 寄存器**：算盘是**教室的公共资源**，学生一离开座位（未被调度器放行执行）就碰不到它、做不了算术——这正是 warp 等内存时"算不了"的物理原因；笔记本是**学生私人物品**，登记入住（**线程驻留**）时就发，走到哪带到哪，warp 切换时数据不丢、也不留在教室——因为寄存器堆在 SM 上、归线程所有，和教室（ALU）是两套独立资源。还要注意：算盘**不能存数**，数据全在笔记本里——坐下后从笔记本抄数、拨算盘、结果记回笔记本。所以**"能不能算"取决于有没有坐上座位（调度器放行），"数在不在"与座位无关**
- **图书馆 = 显存（global memory）**：总书库在校园最外面，借一趟书一来一回好几百周期（**访存显存**）；对比之下，查**微信群**（共享内存）就在楼内、几十周期——**两种"访存"差一个数量级**，这正是 warp 要起身回休息室（warp 切换）、管理员叫下一个班进来（延迟隐藏）的原因。图书馆的书**全校公用**：显存全卡所有线程都能访问（微信群只限本系、笔记本只限本人）。书借回来要先**抄进笔记本（寄存器）**才能拨算盘——"**先搬数据、再算得飞快**"，这就是后面优化"先把数据搬进共享内存再反复用（tiling）"的动机
- **驻留 ≠ 上座**：学生分到某层后先在休息室"登记入住"（**= 线程驻留**：分配寄存器、有了被点名的资格）——**住进来了不代表在算**。这 5 个系 540 人能同时驻留，是因为待命位够多（540 ≪ 6144）；而真正坐在 384 个座位上（12 间教室）的，同一时刻最多 384 人
- **不满的班**：系一最后那个班只有 20 人 → 上座仍要占满 32 个座位（12 个空着）= **不满的 warp**；如果班里学生分成两派要做不同的题，管理员只能先放一边要的 PPT、再放另一边（**warp 发散**），两边轮流听
- **排队/启动条件**：block 太大时整个系上不了楼——假设系六有 **3000 人**（一个 block > 单层休息室 2048 上限），任何一层都收不下它，整个系只能拆成几个小系（**拆小 block**）才能开课；若任务总人数超过全校待命位，晚到的系也要整系在操场等，直到有层腾出休息室（**block 排队**）
- **block 数 5 > 楼层数 3**：硬件通过"一层塞多个系"解决了"block 多于 SM"的矛盾——这正是 GPU 上"网格 block 随便写，硬件自动排兵布阵"的原理

**三个边界澄清**（初学最常问的三个"对不对"）：

- **一个系对应一个 block？——对**：系一 200 人 = 一个 200 线程的 block，整系指派给某一层；上表"系一 200 人（1 个 block）"就是这么来的。block 是"系"，thread 是"学生"
- **共享内存是不是全卡所有线程都能访问？——不是**：共享内存在硬件上按 block 切分，是"系内微信群"——只有本系同学看得见、发得了消息；其他系（哪怕同住一层休息室）既看不见你的群、也发不进你的群。block 之间的共享内存互不可见
- **微信群发消息大家立刻能看到？——不一定**：同学 A 发了消息，同学 B 若不**同步（`__syncthreads()`）**就去读，可能读到**旧值**（乱序执行、缓存延迟所致）。正确姿势是"发 → 等全班齐（`__syncthreads()`）→ 再读"——这正是例子里"要等全班齐了再对答案（同步）"的原因
- **微信群之外还有私人笔记本**：每个学生自己的寄存器、局部变量只有自己看得见，和微信群无关——线程私有数据与 block 共享数据是两码事

> 回到抽象表：**grid 是"要上多少课"，block 是"一个系"，thread 是"一个学生"，而 SM、教室、休息室、管理员（warp 调度器）是教学楼（GPU）自己的事**。程序员只负责排课表（写 grid/block/thread），从不管哪层楼、哪间教室。

> **一句话记忆**：代码写在 thread 里，协作发生在 block 内，并行规模由 grid 撑起来，而硬件真正调度的是 warp。CPU 程序员在 x86 上永远遇不到这一套——这正是 GPU 编程的思维门槛。

### 10.5 教室里的真实装备：一个 warp 到底用什么算

前面的比喻里，教室 = 32 个座位 + 管理员，每个座位一把算盘。真实的教室里**不止有算盘**——warp 的 32 个线程每次坐下，能用的是**这一整套装备**（按"工种"分工，一次一条指令只用其中一件）：

| 教室里的装备 | 硬件单元 | 干什么用 | 类比 |
|---|---|---|---|
| 浮点算盘 | FP32 CUDA Core | 浮点加减乘 | "CUDA Core"本尊，最常见的算术单元 |
| 整数算盘 | INT32 Core | 整数运算、算地址下标 | 与浮点算盘并排，各算各的 |
| 收发员 | LD/ST 单元 | 取数/存数（访存进寄存器） | 跑腿搬运：把显存/共享内存的数据搬进笔记本 |
| 特殊函数器 | SFU | 三角函数、开方、倒数 | 一个按钮直接出函数值 |
| 九九表机 | Tensor Core | 整块矩阵乘（4×4） | 印版/九九乘法表——背下的那几种乘得飞快 |

warp 执行时，管理员把当前那条指令投给对应的装备：算浮点 → 全班坐满浮点算盘；算整数 → 换到整数算盘；访存 → 收发员跑腿；矩阵乘 → 全班把数据塞进九九表机。**一条指令只动一件装备，32 个线程一起用那一件**；不同装备可以同时各有各的班在用（管理员按指令派发），所以算浮点、算整数、访存并不互相挤。

> ⚠️ 两个容易误会的点：①"32 个座位"是"能同时坐 32 人（一个 warp）"，**不等于有 32 个计算单元**——每种装备数量由硬件定、各不相同；②各装备**专精不同**，所以"这台 GPU 算力多大"要看具体指令类型，不能只数 CUDA Core 一个数。

**两代教室的装备清单：GTX 1080（Pascal）vs RTX 2080（Turing）**

Pascal 和 Turing 的 SM 都是 **4 个处理分区 = 4 间教室**，但每间教室的装备不同：

| 每间教室（1 个 SM 分区） | GTX 1080（Pascal） | RTX 2080（Turing） |
|---|---|---|
| 浮点算盘（FP32 CUDA Core） | 32 | 16 |
| 整数算盘（INT32 Core） | 0（整数挤在浮点算盘上拨） | 16 |
| 收发员（LD/ST 单元） | 8 | 8 |
| 特殊函数器（SFU） | 8 | 8 |
| 九九表机（Tensor Core） | **0** | **2** |

按"教室 → 一层楼 → 整栋楼"放大：**一间教室 × 4 = 一层楼（SM），一层楼 × 层数 = 整栋计算大楼（整卡 GPU）**。上一张表给的是"一间教室"的尺度，下面这张拉到"整栋大楼"：

再放大到整栋计算大楼（整卡 GPU，装备总数 = 每层装备 × 层数）：

| 整栋计算大楼（整卡 GPU） | GTX 1080（20 层楼） | RTX 2080（46 层楼） |
|---|---|---|
| SM 数 | 20 | 46 |
| FP32 CUDA Core | 2560 | 2944 |
| INT32 Core | 无（共用 FP32） | 2944 |
| LD/ST 单元 | 640 | 1472 |
| SFU | 640 | 1472 |
| Tensor Core | **0** | **368** |
| 显存 / 带宽 | 8GB GDDR5X / 320 GB/s | 8GB GDDR6 / 448 GB/s |

结论：RTX 2080 相比 1080 只干了两件事——**① 每间教室新添 2 台"九九表机"（Tensor Core），AI 矩阵乘从此有专机**；**② 整数和浮点"分家"**：Pascal 的整数挤在浮点算盘上算（互抢），Turing 各配一把、可以并行（算地址和算浮点互不耽误）。通用算力只是小幅提升（2560 → 2944），真正的质变来自"**加装专用装备**"。

> 对比手头的 A100（Ampere）：每层仍是 4 间教室，每间只放 **1 台更强的第 3 代 Tensor Core**（一次算 4×4×4、支持稀疏），所以"台数"反而少（108 层 × 4 = 432），矩阵乘算力却翻倍——**别按台数比，要看规格**。

> ⚠️ 由此得出本仓库的分工：**原理线（CUDA 内核）在 1080 上跑**，因为没有 Tensor Core 反而"干净"；**LLM 线（FlashAttention、训练）在云端 A100/4090D 上跑**，因为那才是它们的用武之地。

> 💡 九九表机（Tensor Core）就是**混合精度**的硬件根基：输入低精度（FP16/BF16）、累加高精度（FP32），所以"又省又准"。整套概念与 PyTorch AMP 的区分见 §2.3。

## 11. 算力 vs 带宽：为什么 GPU 也要"喂数据"

### 11.1 两个关键数字

GPU 有两项指标，理解它们的配合是性能分析的核心：

- **算力（compute）**：每秒能做多少次运算，单位 **FLOPS**（FLoating-point Operations Per Second，每秒浮点运算次数），**TFLOPS = 每秒万亿次**（如 GTX 1080 约 8.9 TFLOPS FP32，A100 约 19.5 TFLOPS FP32）
- **带宽（bandwidth）**：每秒能从显存读多少字节（GTX 1080 约 320 GB/s，A100 约 1555 GB/s）

### 11.2 算术强度：把数据多用几次

**算术强度（arithmetic intensity）= 每个字节数据被用了几次（FLOP/B，FLOP 指一次浮点运算）**。它是性能的"天气指标"：

| 算术强度 | 行为 | 瓶颈 | 对策 |
|---|---|---|---|
| 低（如向量加法 `c=a+b`） | 读 2 个数、写 1 个数、算 1 次 | **带宽**（数据喂不过来） | 减少重复读、合并访问 |
| 高（如矩阵乘，一个元素用 N 次） | 每个数据被反复算 | **算力** | 用满 CUDA Core/Tensor Core |

> 一个数字感受一下：GTX 1080 算力 8.9 TFLOPS、带宽 320 GB/s，若一次运算要读 1 字节，算术强度 ≥ 8.9e12 / 320e9 ≈ **28 FLOP/B** 才能喂饱算力。像 `a[i]=b[i]+c[i]` 这种只有 0.5 FLOP/B 的活，GPU 再快也被带宽锁死。所以 GPU 的甜蜜点是**让每个数据被反复利用**的算法——矩阵乘正是教科书级例子。

### 11.3 Roofline：一张图判断瓶颈

把"算术强度"画在横轴、"可达性能"画在纵轴，就得到 **Roofline 模型**——一条屋顶线+一条斜坡线：

- **斜坡区**（数据喂不过来）：性能受带宽限制，加了算力也没用
- **屋顶区**（算力用满）：性能受算力限制，还能靠提高算术强度（复用数据）再往上走

后面做矩阵乘优化时，你会亲身体会：naive 版本在斜坡区（被带宽卡死），tiling 让数据在共享内存反复复用后冲上屋顶区。**Roofline 是本章最重要的性能心智模型。**

## 12. 什么任务才适合 GPU

### 12.1 判断标准

判断标准两条，缺一不可：

1. **可并行**：能拆成大量相互独立的小块（互不依赖才能同时算）
2. **计算密集 / 数据复用高**：算的时间 >> 搬数据的时间（别让内存带宽成为瓶颈）

| 适合 GPU | 不适合 GPU |
|---|---|
| 矩阵乘法、卷积 | 串行依赖（迭代求解、链表遍历） |
| 深度学习训练/推理 | 逻辑复杂、分支多的小任务 |
| 图像/视频处理 | 频繁全局同步 |
| 海量数据科学计算 | I/O 密集（瓶颈在磁盘/网络） |

> 很多"不适合 GPU"的任务换个算法就适合了：链表遍历可改连续数组；串行迭代可能用并行归约替代。**算法形态决定了能否上 GPU。**

## 15. 常见问题（FAQ）

**Q：GPU 那么多核心，为什么不能替代 CPU？**
A：GPU 核心极简，没有乱序执行、分支预测、大缓存，不适合分支多的复杂逻辑；且 GPU 要 CPU 指挥（kernel 由 CPU 发起）、数据要在 CPU 内存和显存间搬。两者分工协作。

**Q：主频那么高，是不是主频越高越好？**
A：主频只是单条指令的快慢；同频下，架构（流水线、SIMD、核数）决定吞吐。GPU 主频远低于 CPU（约 1.5 GHz），但靠海量核心取胜。

**Q：为什么 GPU 算矩阵乘比 CPU 快这么多？**
A：矩阵乘是可并行+高算术强度（数据复用极高）的完美任务：块内可完全并行、且每个数据用 N 次。CPU 只有 8~64 个核 × 8 宽 SIMD，GPU 是几千个核 × 32 宽 warp，规模差两个数量级。

**Q：我的程序用了多线程，为什么没变快？**
A：可能是串行部分太大（Amdahl）、线程太多被调度拖慢、或数据在内存不连续导致缓存/带宽瓶颈。先分析瓶颈再谈并行。

## 小结

- CPU 是"少数全能冠军"：优化单线程延迟（流水线/乱序/分支预测/缓存），线程"又大又少"
- 从高级语言到机器码经过编译；数据在内存里按二进制存，浮点数按 IEEE 754 存（精度有限）；混合精度"低精度算、FP32 攒"是 GPU 硬件/CUDA 的能力，Tensor Core 支撑
- 单核被功耗墙锁死，多核核数上不去（8~64），所以 CPU 并行度有限
- CPU 早就有 SIMD（AVX 一条指令算 8 个数）——GPU 的 SIMT 就是把它放大到极致
- GPU 是"海量重复工人"：优化整体吞吐，线程"又小又多"，靠数量藏住内存延迟
- 程序里线程按 grid → block → thread 组织，block 内可协作、block 间独立；硬件按 warp（32 线程）调度
- GPU 的瓶颈可能是算力也可能是带宽；用**算术强度 / Roofline** 判断
- 任务适不适合 GPU：看是否"可并行 + 数据复用高"
