# 03 GPU 内存模型：寄存器、共享内存、全局内存与合并访问

> 对应里程碑 M2。前两篇讲清了"GPU 为什么快"（00_why_gpu.md）和"线程怎么组织"（02_cuda_basics.md）。本篇回答下一个关键问题：**线程在算的时候，数据是从哪拿的？** GPU 的内存不像 CPU 那样只有一个大内存，而是一个**有快慢、分大小、各有用途的层级结构**——用错一层，性能可能差一个数量级。

**阅读路线**：先记住整个内存金字塔（§1），再逐层看清每种内存的"速度、容量、归谁用"（§2~§7），最后重点掌握本文件的核心技能——**合并访问**（§8）和一个经典陷阱——**矩阵转置**（§9）。读完你应能回答：为什么"随便写"的 GPU 程序跑不快？怎么让显存带宽喂满？

## 1. 内存层级总览：GPU 也有一个"金字塔"

和 CPU 一样，GPU 的内存也是**越靠近计算单元越快、越小、越贵**：

```
                      计算单元（SM 里的 CUDA Core）
                       ▲ 寄存器 Registers    （~1 周期，每线程几十字节）
                       │
          ┌────────────┼────────────┐
          │ 共享内存 Shared Memory │   （~20 周期，每 block 最多几十 KB）
          │ 常量/纹理缓存          │
          └────────────┼────────────┘
                       │
                L2 缓存（芯片上，多 SM 共享）
                       │
               全局内存 Global Memory = 显存 VRAM
               （~200-400 周期，几十 GB 容量，带宽极高）
                       │
               主机内存（CPU RAM，PCIe 搬运，最慢的一次）
```

**先把最关键的三层记牢**：

| 内存 | 谁在用 | 速度 | 容量 | 一句话 |
|---|---|---|---|---|
| 寄存器 | **每个线程独有** | ~1 周期 | 每线程几十个 | 线程的"速记本"，装正在算的数 |
| 共享内存 | **每个 block 内共享** | ~20 周期 | 每 block 几十 KB | block 内线程的"公共黑板" |
| 全局内存（显存） | **所有线程共享** | ~200-400 周期 | 几 GB~几十 GB | 数据的大本营，所有线程都能访问 |
| 常量内存 | 所有线程只读 | 缓存命中时快 | 64 KB | 存"所有人读同一份"的小常量表 |
| 本地内存 | 每个线程独有 | 慢（其实是全局内存） | — | 寄存器不够时溢出的"备胎" |

> 一句话直觉：**GPU 编程就是"少访问全局内存、多用寄存器/共享内存"的游戏**。全局内存虽然带宽巨大（GTX 1080 约 320 GB/s），但延迟是寄存器的几百倍；而 GPU 正是靠海量线程轮换来掩盖这个延迟（见 02_cuda_basics.md §2.5 的"延迟隐藏"）。

## 2. 寄存器（Registers）：线程的"速记本"

**寄存器是每根线程的私有财产**，装的是这个线程正在计算的中间结果（循环变量、局部变量等）。

- 每个 SM 有 **65536 个 32 位寄存器**，分配给驻留在该 SM 上的所有线程
- 编译器自动分配，程序员**一般不直接控制**（只能通过 `-maxrregcount` 或 `__launch_bounds__` 间接限制）
- 一个线程用到的寄存器数量，**直接决定 SM 能驻留多少个线程**：

```
假设一个 SM 有 65536 个寄存器：
  若每线程用 32 个 → 65536 / 32 = 2048 线程驻留
  若每线程用 255 个 → 65536 / 255 ≈ 257 线程驻留

线程驻留得少 → warp 少 → 延迟隐藏能力变差 → 性能下降
```

> ⚠️ 关键权衡：**寄存器用得越少，能驻留的线程越多**（occupancy 越高，详见 04_performance.md），但每个线程可用的"工作台"也越小，代码可能被"挤出去"（见 §3）。一般目标是每线程 **32~64 个寄存器**，既够用又能保持高 occupancy。

---

## 3. 本地内存（Local Memory）：寄存器不够时的"备胎"

当线程的寄存器不够用了（局部数组过大、分支太多、编译器没法全部塞进寄存器），溢出的变量会被放到**本地内存**：

- ⚠️ 名字叫 "local"，**但物理上就在全局内存里**，走同样的 L2 缓存，延迟和全局内存一个量级——**慢**
- 只有**自己**能访问，所以逻辑上还是"私有"的
- 用 `nvcc -Xptxas -v` 编译能看到每线程用了多少寄存器、多少本地内存

**怎么避免**：少用超大局部数组；把大数组放到共享内存；必要时用 `__launch_bounds__` 告诉编译器"我要少用寄存器"。

---

## 4. 共享内存（Shared Memory）：block 内线程的"公共黑板"

### 4.1 它是什么

每个 **block** 拥有一块**私有的高速内存**，块内所有线程都可以读写，块与块之间**不可见、不互通**。

- 速度：~20 周期（比全局内存快一个数量级）
- 容量：Pascal（GTX 1080）每 SM 96 KB，**默认每 block 最多 48 KB**（可通过 `cudaFuncSetAttribute` 申请更多）
- 声明：`__shared__`；动态大小用 `extern __shared__ float sm[]` + 启动配置第三个参数

```cuda
__shared__ float tile[256];   // 静态共享内存：编译期定死大小

// 动态共享内存：
extern __shared__ float sm[]; // 大小在启动时由 <<<..., bytes>>> 指定
kernel<<<grid, block, 256 * sizeof(float)>>>(...);
```

### 4.2 典型用法：矩阵乘法的"分块复用"

全局内存访问很贵，但如果一小块数据**会被多次重复读**，就值得先搬进共享内存，再让块内线程反复用：

```
naive 矩阵乘：每个线程每算一次累加，就重读一遍 A[i][k] 和 B[k][j]
  → 一共读了 O(N³) 次全局内存，浪费带宽

分块（tiling）后：
  → 每次把 A/B 的一小块（tile）拷进共享内存
  → 块内线程反复读共享内存（快）
  → 全局内存只读了 O(N³ / tile²) 次
```

这就是 `code/04_optimization/` 里矩阵乘 `naive → shared → tiling` 演进的核心动机，也是 cuBLAS、FlashAttention 一切优化的起点。

### 4.3 同步：`__syncthreads()`

共享内存是**块内所有线程共用的**，就存在"线程 A 正在写、线程 B 却在读"的竞争问题。块内需要用**栅栏**同步：

```cuda
__shared__ float tile[256];

// 所有线程把自己的那份拷进来
tile[tid] = global_data[tid];
__syncthreads();      // 等全 block 都拷完，再往下走
// 之后任何人都可以安全读 tile
```

- `__syncthreads()` 是 **block 内**的同步点：所有线程执行到这里必须"会合"后才能继续
- ⚠️ **block 之间无法同步**（这正是 02_cuda_basics.md §5.2 说的"block 相互独立"的原因）；跨 block 协作必须靠多次 kernel 启动或全局内存 + 原子操作
- ⚠️ block 内**不同分支里的 `__syncthreads()` 会导致死锁**（warp 发散，见 04_performance.md）

### 4.4 陷阱：bank conflict（bank 冲突）

共享内存在物理上分成 **32 个 bank（银行）**，每个 bank 一个周期只能服务一次访问。一个 warp 里 32 个线程**同一时刻**去访问共享内存：

```
理想情况：32 个线程各自访问 32 个不同的 bank → 1 个周期搞定 ✅
坏情况：   32 个线程挤到同一个 bank       → 串行排队 → 慢到 32 倍 ❌
```

```cuda
__shared__ float sm[1024];

// 没有冲突：thread t 访问 sm[t] → 正好落在不同 bank
float a = sm[tid];

// 有冲突：stride = 32，所有线程都撞到同一个 bank！
//        （32 的倍数地址会落在同一个 bank 上）
float b = sm[tid * 32];
```

**常见缓解**：
- 访问 `sm[tid]` 或 `sm[tid + offset]`（连续、错位）通常没事
- 对二维数组 `sm[row][col]`，注意**行长**避免恰好是 32 的倍数
- 给数组**填充（padding）**一列，把自然错开成 bank 边界（如 `sm[BLOCK][BLOCK+1]`）

> 初次接触不用背细节，只要记住一句话：**共享内存里，相邻线程最好访问相邻地址**——这既是合并访问（§8）的规则，也是避免 bank conflict 的规则。

## 5. 全局内存（Global Memory）：数据的大本营 = 显存

### 5.1 它是什么

全局内存就是我们说的**显存（VRAM）**。所有线程都能读写，host 侧也能通过 `cudaMemcpy` 搬进搬出。

| 属性 | 值（GTX 1080 参考） |
|---|---|
| 容量 | 8 GB |
| 带宽 | ~320 GB/s（比 CPU 内存的 ~50 GB/s 快 6 倍） |
| 延迟 | ~200-400 周期 |
| 分配 | `cudaMalloc` / `cudaFree` |
| 搬运 | `cudaMemcpy`（H2D / D2H），走 PCIe，慢 |

```cuda
float *d_a;
cudaMalloc(&d_a, n * sizeof(float));                                 // 显存分配
cudaMemcpy(d_a, h_a, n * sizeof(float), cudaMemcpyHostToDevice);     // 搬进
// ... 在 GPU 上算 ...
cudaMemcpy(h_c, d_c, n * sizeof(float), cudaMemcpyDeviceToHost);     // 搬出
cudaFree(d_a);
```

### 5.2 全局内存访问的单位是"事务"，不是字节

这是**全篇最重要的一条硬件事实**：

> GPU 访问全局内存时，不是一次读 1 个 float（4 字节），而是**一次搬一整块**（128 字节的 cache line，称为一个 memory transaction）。

一个 warp 的 32 个线程**同时发起访问**，硬件把它们合并成**尽量少的几个 128 字节事务**。合并得好不好，决定带宽利用率——这就是下一节要讲的**合并访问**。

## 6. 常量内存（Constant Memory）：只读的小广播

- 大小固定 **64 KB**，用 `__constant__` 声明，host 用 `cudaMemcpyToSymbol` 写入
- 特点：**当 warp 内所有线程访问同一地址**时最快——硬件会"广播"给所有线程，1 个周期搞定
- 适合：系数表、卷积核、LLM 里的固定配置等"所有人读同一份"的数据
- ⚠️ 如果 warp 内各线程**访问不同地址**，常量内存会按地址个数**串行化**，反而比全局内存还慢

```cuda
__constant__ float conv_weights[64];   // 声明在全局作用域

// host 侧写入
float h_w[64] = {...};
cudaMemcpyToSymbol(conv_weights, h_w, sizeof(h_w));
```

---

## 7. 纹理内存 / 表面内存（简述）

老 API，用"纹理缓存"加速**二维/三维局部性好的只读访问**，并内置插值、边界处理。深度学习时代用途很少，了解存在即可；需要"相邻像素"强局部性的图像类算法可能用到。

## 8. 合并访问（Coalescing）：喂满带宽的第一课

### 8.1 什么是"合并"

**合并访问** = 一个 warp 里的 32 个线程，**尽量访问连续（相邻）的内存地址**，让硬件把它们合并成最少的 memory transaction：

```
✅ 合并（coalesced）：
   32 个线程 → 连续 128 字节 → 1 个事务
   线程0: 读 a[0]    线程1: 读 a[1]   ...  线程31: 读 a[31]

❌ 未合并（stride 访问）：
   32 个线程 → 各读一个远隔 4 KB 的数 → 32 个事务
   线程0: 读 a[0]    线程1: 读 a[1024]  ...  线程31: 读 a[31744]
```

### 8.2 为什么有合并、没合并差距巨大

带宽是 GPU 的命脉。以 GTX 1080 的 320 GB/s 为例：

```
场景 A（合并）：
  每个线程读 4 字节，1 个事务 128 字节喂饱 32 个线程
  → 带宽利用率 ~100%

场景 B（每个线程跳着读）：
  每个线程还是要那 4 字节，但事务要 32 个
  → 实际搬了 32×128 = 4096 字节，有用的只有 128 字节
  → 带宽利用率 ~3%，其余 97% 白搬
```

**结论：未合并访问 ≈ 带宽利用率打 1/30 的折扣**。这就是为什么 "GPU 程序快不快，常常第一个看内存访问是不是合并的"。

### 8.3 怎么写才是合并的？——看 threadIdx 映射到哪个下标

规则很简单：**让 `threadIdx.x` 连续变化时，访问的地址也连续变化**。

```cuda
// ✅ 合并：i = tid + blockIdx*blockDim，相邻线程访问相邻地址
int i = threadIdx.x + blockIdx.x * blockDim.x;
c[i] = a[i] + b[i];          // 02_cuda_basics.md §4.3 的 vec_add 就是典型的

// ❌ 未合并：线程号乘了个 8，32 个线程各隔 8 个元素
int j = (threadIdx.x + blockIdx.x * blockDim.x) * 8;
c[j] = a[j] + b[j];
```

> 注意一个反直觉点：合并访问跟**程序员分配数据的方式**无关（显存里就是一块连续内存），只看**线程号怎么映射到下标**。`threadIdx.x` 乘个非 1 的数，或者按列访问行主序数组，就会破坏合并。

### 8.4 一个真实案例：先理解"按行存"的代价

矩阵在显存里通常**按行连续存储（row-major）**。假设一个 4×4 的 float 矩阵：

```
内存布局（row-major）：[r0c0, r0c1, r0c2, r0c3, r1c0, r1c1, ...]

按行处理（thread t → 行 t 的第 col 列）：相邻线程访问相邻地址 → 合并 ✅
按列处理（thread t → 第 t 行的列）：相邻线程访问相隔一行的地址 → 不合并 ❌
```

这个"行列陷阱"在**矩阵转置**里体现得最典型，下一节实战验证。

## 9. 实战案例：矩阵转置的"合并访问陷阱"

任务：把 `N×N` 矩阵转置，`out[j][i] = in[i][j]`。

### 9.1 两种写法，一种快一种慢

```cuda
// 写法 A：读合并，写不合并
// 每个线程读一行里的连续元素（合并 ✅），写回转置位置时是列方向（不合并 ❌）
int i = blockIdx.y * blockDim.y + threadIdx.y;   // 行
int j = blockIdx.x * blockDim.x + threadIdx.x;   // 列
out[j][i] = in[i][j];   // 按行读入 → 合并；按列写出 → 不合并

// 写法 B：把数据经共享内存转一道，两边都合并 ✅✅
// 1) 连续读进共享内存（合并） 2) 从共享内存转置读出（合并）
__shared__ float tile[TILE][TILE+1];   // +1 是 padding，防 bank conflict
```

**为什么写法 A 总有一边不合并**：一个 warp 的 32 个线程，`threadIdx.x` 连续 → 读 `in[i][j]` 时 `j` 连续 → 读合并；但写 `out[j][i]` 时是**行下标**连续 → 跨行写 → 写不合并。读写总有一头吃亏。

### 9.2 用共享内存"转个弯"，两头都合并

```
1. 全体线程连续读 in 的一小块（合并 ✅）→ 存进共享内存 tile
2. __syncthreads()
3. 从 tile 里按转置后的顺序连续写 out（合并 ✅）
```

共享内存充当"转置中转站"，把"不合并"的读写挡在高速的共享内存一侧。这就是 `code/03_memory/` 里的练习，也是很多高性能 kernel 的通用套路：**用共享内存把访存模式"捋直"**。

> 💡 小结：合并访问不只靠"写对下标"，还常需要**配合共享内存**来改变数据的流动方向。先看懂 9.1，再跑一遍 9.2，合并访问这个概念就扎实了。

## 10. 一张表总结 & 性能检查清单

### 10.1 内存速查表

| 内存 | 声明/分配 | 作用域 | 速度 | 容量 | 关键注意 |
|---|---|---|---|---|---|
| 寄存器 | 局部变量 | 线程私有 | ~1 周期 | 每线程几十个 | 用得多会挤掉 occupancy |
| 本地内存 | 溢出的局部变量 | 线程私有 | 慢（实为全局内存） | — | 尽量避免 |
| 共享内存 | `__shared__` | block 内共享 | ~20 周期 | 最多 ~48 KB/block | 要同步、防 bank conflict |
| 全局内存 | `cudaMalloc` | 所有线程 | ~200-400 周期 | 几 GB~几十 GB | **必须合并访问** |
| 常量内存 | `__constant__` | 所有线程只读 | 同地址广播快 | 64 KB | 各线程访问不同地址会变慢 |
| 纹理/表面 | API 绑定 | 所有线程只读 | 有纹理缓存 | 任意 | 图像类局部性好时用 |

### 10.2 写完一个 kernel 自问 5 句

1. **全局内存访问合并了吗？** `threadIdx.x` 连续 ↔ 地址连续？没有 → 立刻改
2. **数据有反复复用吗？** 有 → 搬进共享内存，别反复读显存
3. **共享内存够不够？** 超出 48 KB 每 block 了？要动态申请或减小 tile
4. **写共享内存后 `__syncthreads()` 了吗？** 没同步就读写 → 数据竞争
5. **寄存器用太多了吗？** 编译看 `-Xptxas -v`，超 128 个要小心 occupancy
