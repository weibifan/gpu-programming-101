## 1. 内存层级总览：GPU 也有一个"金字塔"

和 CPU 一样，GPU 的内存也是**越靠近计算单元越快、越小、越贵**。这里的"内存"指 **GPU 侧**的所有存储（寄存器 → 缓存 → 显存）；**主机内存（CPU RAM）在另一台"机器"上**，只能靠 `cudaMemcpy` 走 PCIe 搬运，是最底层且最慢的。但学之前先分清两个词，否则后面会被"本地内存""常量内存"这些名字绕晕：

- **物理层级**：数据真正存放在哪（硬件上真实存在的存储器，就那么几层）
- **逻辑概念**：编程时"谁能用、归谁管"（编译器/API 给你的使用方式，名字一大堆）

### 1.1 物理视角 vs 逻辑视角：一张表看懂

同一块硬件用两个视角看就不乱了。**第一列是物理层（数据真正住在哪，从上到下越来越慢），第二列是编程时的名字（逻辑概念）**，同一行表示"这些名字就住在这一层"：

| 物理视角：数据真正住在哪 | 逻辑视角：编程时的名字（谁在用） |
|---|---|
| 寄存器 Registers（~1 周期，每线程几十字节） | 寄存器变量——线程私有 |
| L1 缓存（每 SM 一片内 SRAM，~20-30 周期） | 共享内存——block 独占（就是从这块 L1 划出来的） |
| L2 缓存（芯片上所有 SM 共用，~100-200 周期） | （L1/L2 自动缓存，程序员不直接管） |
| 全局内存 = 显存 VRAM（~200-400 周期，几十 GB） | 全局内存变量——所有线程共享；本地内存——寄存器溢出也住这（慢）；常量内存——64 KB 只读，走常量缓存；纹理内存——只读，走纹理缓存 |
| 主机内存（CPU RAM，PCIe 搬运，最慢） | host 变量（cudaMemcpy 搬进搬出） |

真正的物理层只有 **寄存器 → L1 缓存 → L2 缓存 → 全局内存（显存）→ 主机内存** 五级。**共享内存、本地内存、常量内存、纹理内存都不是新层**，只是编程时的名字——分别对应"L1 划出的一块""全局内存的兜底地址""全局内存的只读通路"。

> 💡 关于 L1 与共享内存：**L1 缓存是每块 SM 的片内 SRAM，硬件自动管**，用来缓存全局内存/本地内存的读取；**共享内存是从这块 SRAM 里划出的一块**（运行时按比例划分），归程序员用 `__shared__` 手动管。所以寄存器溢出的本地内存访问会命中 L1/L2，比直接读显存稍快。L2 则是**所有 SM 共用**的，在更下面一层。

### 1.2 逻辑概念对照表：编程时的"名字" vs 数据实际住在哪

编程时你会碰到一堆"内存名字"，它们**大多不是新的一层**——数据最终都落在 1.1 的物理层里：

| 逻辑概念（编程名字） | 谁在用（作用域） | 数据物理上住在哪 | 速度 | 容量 | 一句话 |
|---|---|---|---|---|---|
| 寄存器 | **每个线程独有** | 寄存器（真物理层） | ~1 周期 | 每线程几十个 | 线程的"速记本"，装正在算的数 |
| 共享内存 | **每个 block 内共享** | 从 L1 缓存（片内 SRAM）划出的一块（§1.1） | ~20 周期 | 每 block 几十 KB | block 内线程的"公共黑板" |
| 全局内存 | **所有线程共享** | 显存 VRAM（真物理层） | ~200-400 周期 | 几 GB~几十 GB | 数据的大本营，所有线程都能访问 |
| 本地内存 | 每个线程独有 | **其实在全局内存里**（§2.2） | 慢（同全局内存） | — | 寄存器不够时溢出的"备胎" |
| 常量内存 | 所有线程只读 | **也在全局内存里**（64 KB 区域），走常量缓存（§4.3） | 缓存命中时快 | 64 KB | 存"所有人读同一份"的小常量表 |
| 纹理内存 | 所有线程只读 | **数据也在全局内存里**，走纹理缓存（§4.4） | 有纹理缓存加速 | 任意 | 图像类局部性好时用 |

> 一句话直觉：**GPU 编程就是"少访问全局内存、多用寄存器/共享内存"的游戏**。全局内存（显存）虽然带宽巨大（GTX 1080 约 320 GB/s），但延迟是寄存器的几百倍；而 GPU 正是靠海量线程轮换来掩盖这个延迟（见 02_cuda_basics.md §3.2 的"延迟隐藏"）。

## 2. 寄存器与本地内存：线程的"速记本"和它的"备胎"

这一层只属于**单个线程**：寄存器装正在算的数，装不下就溢到"本地内存"（物理上其实是全局内存）。两者共同决定线程的"工作台"有多大。

### 2.1 寄存器（Registers）：线程的"速记本"

**寄存器是每根线程的私有财产**，装的是这个线程正在计算的中间结果（循环变量、局部变量等）。

- 每个 SM 有 **65536 个 32 位寄存器**，分配给驻留在该 SM 上的所有线程
- 编译器自动分配，程序员**一般不直接控制**（只能通过 `-maxrregcount` 或 `__launch_bounds__` 间接限制）
- 一个线程用到的寄存器数量，**直接决定 SM 能驻留多少个线程**：

```
假设一个 SM 有 65536 个寄存器：
  若每线程用 32 个 → 65536 / 32 = 2048 线程驻留
  若每线程用 255 个 → 65536 / 255 ≈ 257 线程驻留

线程驻留得少 → warp 少 → 延迟隐藏能力变差 → 性能下降
```

> ⚠️ 关键权衡：**寄存器用得越少，能驻留的线程越多**（occupancy 越高，详见 §8），但每个线程可用的"工作台"也越小，代码可能被"挤出去"（见 2.2）。一般目标是每线程 **32~64 个寄存器**，既够用又能保持高 occupancy。

### 2.2 本地内存（Local Memory）：寄存器不够时的"备胎"

当线程的寄存器不够用了（局部数组过大、分支太多、编译器没法全部塞进寄存器），溢出的变量会被放到**本地内存**：

- ⚠️ 名字叫 "local"，**但物理上就在全局内存里**，走同样的 L2 缓存，延迟和全局内存一个量级——**慢**
- 只有**自己**能访问，所以逻辑上还是"私有"的
- 用 `nvcc -Xptxas -v` 编译能看到每线程用了多少寄存器、多少本地内存

**怎么避免**：少用超大局部数组；把大数组放到共享内存；必要时用 `__launch_bounds__` 告诉编译器"我要少用寄存器"。

## 3. 共享内存（Shared Memory）：block 内线程的"公共黑板"

### 3.1 它是什么

每个 **block** 拥有一块**私有的高速内存**，块内所有线程都可以读写，块与块之间**不可见、不互通**。

> 物理上它就是 §1.1 说的**从 SM 的 L1 缓存（片内 SRAM）里划出的一块**——所以它和 L1 是同一片物理 SRAM，只是归程序员手动管、归 block 独占。

- 速度：~20 周期（比全局内存快一个数量级）
- 容量：Pascal（GTX 1080）每 SM 96 KB，**默认每 block 最多 48 KB**（可通过 `cudaFuncSetAttribute` 申请更多）
- 声明：`__shared__`；动态大小用 `extern __shared__ float sm[]` + 启动配置第三个参数

```cuda
__shared__ float tile[256];   // 静态共享内存：编译期定死大小

// 动态共享内存：
extern __shared__ float sm[]; // 大小在启动时由 <<<..., bytes>>> 指定
kernel<<<grid, block, 256 * sizeof(float)>>>(...);
```

### 3.2 典型用法：矩阵乘法的"分块复用"

全局内存访问很贵，但如果一小块数据**会被多次重复读**，就值得先搬进共享内存，再让块内线程反复用：

```
naive 矩阵乘：每个线程每算一次累加，就重读一遍 A[i][k] 和 B[k][j]
  → 一共读了 O(N³) 次全局内存，浪费带宽

分块（tiling）后：
  → 每次把 A/B 的一小块（tile）拷进共享内存
  → 块内线程反复读共享内存（快）
  → 全局内存只读了 O(N³ / tile²) 次
```

这就是 `code/04_optimization/` 里矩阵乘 `naive → shared → tiling` 演进的核心动机，也是 cuBLAS、FlashAttention 一切优化的起点。

### 3.3 同步：`__syncthreads()`

共享内存是**块内所有线程共用的**，就存在"线程 A 正在写、线程 B 却在读"的竞争问题。块内需要用**栅栏**同步：

```cuda
__shared__ float tile[256];

// 所有线程把自己的那份拷进来
tile[tid] = global_data[tid];
__syncthreads();      // 等全 block 都拷完，再往下走
// 之后任何人都可以安全读 tile
```

- `__syncthreads()` 是 **block 内**的同步点：所有线程执行到这里必须"会合"后才能继续
- ⚠️ **block 之间无法同步**（这正是 02_cuda_basics.md §6.4 说的"block 相互独立"的原因）；跨 block 协作必须靠多次 kernel 启动或全局内存 + 原子操作
- ⚠️ block 内**不同分支里的 `__syncthreads()` 会导致死锁**（warp 发散，见本篇性能部分 §8~§14）

### 3.4 陷阱：bank conflict（bank 冲突）

共享内存在物理上分成 **32 个 bank（银行）**，每个 bank 一个周期只能服务一次访问。一个 warp 里 32 个线程**同一时刻**去访问共享内存：

```
理想情况：32 个线程各自访问 32 个不同的 bank → 1 个周期搞定 ✅
坏情况：   32 个线程挤到同一个 bank       → 串行排队 → 慢到 32 倍 ❌
```

```cuda
__shared__ float sm[1024];

// 没有冲突：thread t 访问 sm[t] → 正好落在不同 bank
float a = sm[tid];

// 有冲突：stride = 32，所有线程都撞到同一个 bank！
//        （32 的倍数地址会落在同一个 bank 上）
float b = sm[tid * 32];
```

**常见缓解**：
- 访问 `sm[tid]` 或 `sm[tid + offset]`（连续、错位）通常没事
- 对二维数组 `sm[row][col]`，注意**行长**避免恰好是 32 的倍数
- 给数组**填充（padding）**一列，把自然错开成 bank 边界（如 `sm[BLOCK][BLOCK+1]`）

> 初次接触不用背细节，只要记住一句话：**共享内存里，相邻线程最好访问相邻地址**——这既是合并访问（§5）的规则，也是避免 bank conflict 的规则。

## 4. 全局内存（显存）与它的只读变体

这一层是所有线程都能碰的**大本营**。常量内存、纹理内存**不是新层**——它们的数据也都住在显存里，只是换了条"只读高速通路"去读。

### 4.1 全局内存（Global Memory）：数据的大本营 = 显存

全局内存就是我们说的**显存（VRAM）**。所有线程都能读写，host 侧也能通过 `cudaMemcpy` 搬进搬出。

| 属性 | 值（GTX 1080 参考） |
|---|---|
| 容量 | 8 GB |
| 带宽 | ~320 GB/s（比 CPU 内存的 ~50 GB/s 快 6 倍） |
| 延迟 | ~200-400 周期 |
| 分配 | `cudaMalloc` / `cudaFree` |
| 搬运 | `cudaMemcpy`（H2D / D2H），走 PCIe，慢 |

```cuda
float *d_a;
cudaMalloc(&d_a, n * sizeof(float));                                 // 显存分配
cudaMemcpy(d_a, h_a, n * sizeof(float), cudaMemcpyHostToDevice);     // 搬进
// ... 在 GPU 上算 ...
cudaMemcpy(h_c, d_c, n * sizeof(float), cudaMemcpyDeviceToHost);     // 搬出
cudaFree(d_a);
```

### 4.2 全局内存访问的单位是"事务"，不是字节

这是**全篇最重要的一条硬件事实**：

> GPU 访问全局内存（显存）时，不是一次读 1 个 float（4 字节），而是**一次搬一整块**（128 字节的 cache line，称为一个 memory transaction）。

一个 warp 的 32 个线程**同时发起访问**，硬件把它们合并成**尽量少的几个 128 字节事务**。合并得好不好，决定带宽利用率——这就是下一节要讲的**合并访问**。

### 4.3 只读变体一：常量内存（Constant Memory）：只读的小广播

- 大小固定 **64 KB**，用 `__constant__` 声明，host 用 `cudaMemcpyToSymbol` 写入
- ⚠️ 物理位置：这块 64 KB **其实也在全局内存（显存）里**（§1.2），只是因为走的通路不同——专门的**常量缓存**——所以读起来比普通全局内存快
- 特点：**当 warp 内所有线程访问同一地址**时最快——硬件会"广播"给所有线程，1 个周期搞定
- 适合：系数表、卷积核、LLM 里的固定配置等"所有人读同一份"的数据
- ⚠️ 如果 warp 内各线程**访问不同地址**，常量内存会按地址个数**串行化**，反而比全局内存还慢

```cuda
__constant__ float conv_weights[64];   // 声明在全局作用域

// host 侧写入
float h_w[64] = {...};
cudaMemcpyToSymbol(conv_weights, h_w, sizeof(h_w));
```

### 4.4 只读变体二：纹理内存 / 表面内存（简述）

老 API。⚠️ 它也不是独立的内存层：**数据同样放在全局内存里**，只是改经**纹理缓存**这条高速通路去读（§1.2），加速**二维/三维局部性好的只读访问**，并内置插值、边界处理。深度学习时代用途很少，了解存在即可；需要"相邻像素"强局部性的图像类算法可能用到。

## 5. 合并访问（Coalescing）：喂满带宽的第一课

### 5.1 什么是"合并"

> ⚠️ 先限定对象：**合并访问说的是线程访问"全局内存 = 显存"，跟主机内存（CPU RAM）无关**。GPU 线程能直接访问的只有显存；数据在主机内存里时，得先由 `cudaMemcpy` 搬进显存，才轮到 warp 去读、才有"合并不合并"的问题。

**合并访问** = 一个 warp 里的 32 个线程，**尽量访问连续（相邻）的显存地址**，让硬件把它们合并成最少的 memory transaction：

```
✅ 合并（coalesced）：
   32 个线程 → 连续 128 字节 → 1 个事务
   线程0: 读 a[0]    线程1: 读 a[1]   ...  线程31: 读 a[31]

❌ 未合并（stride 访问）：
   32 个线程 → 各读一个远隔 4 KB 的数 → 32 个事务
   线程0: 读 a[0]    线程1: 读 a[1024]  ...  线程31: 读 a[31744]
```

### 5.2 为什么有合并、没合并差距巨大

带宽是 GPU 的命脉。以 GTX 1080 的**显存带宽** 320 GB/s 为例：

```
场景 A（合并）：
  每个线程读 4 字节，1 个事务 128 字节喂饱 32 个线程
  → 带宽利用率 ~100%

场景 B（每个线程跳着读）：
  每个线程还是要那 4 字节，但事务要 32 个
  → 实际搬了 32×128 = 4096 字节，有用的只有 128 字节
  → 带宽利用率 ~3%，其余 97% 白搬
```

**结论：未合并访问 ≈ 带宽利用率打 1/30 的折扣**。这就是为什么 "GPU 程序快不快，常常第一个看内存访问是不是合并的"。

### 5.3 怎么写才是合并的？——看 threadIdx 映射到哪个下标

规则很简单：**让 `threadIdx.x` 连续变化时，访问的地址也连续变化**。

```cuda
// ✅ 合并：i = tid + blockIdx*blockDim，相邻线程访问相邻地址
int i = threadIdx.x + blockIdx.x * blockDim.x;
c[i] = a[i] + b[i];          // 02_cuda_basics.md §5.3 的 vec_add 就是典型的

// ❌ 未合并：线程号乘了个 8，32 个线程各隔 8 个元素
int j = (threadIdx.x + blockIdx.x * blockDim.x) * 8;
c[j] = a[j] + b[j];
```

> 注意一个反直觉点：合并访问跟**程序员分配数据的方式**无关（显存里就是一块连续内存），只看**线程号怎么映射到下标**。`threadIdx.x` 乘个非 1 的数，或者按列访问行主序数组，就会破坏合并。

### 5.4 一个真实案例：先理解"按行存"的代价

矩阵在显存里通常**按行连续存储（row-major）**。假设一个 4×4 的 float 矩阵：

```
内存布局（row-major）：[r0c0, r0c1, r0c2, r0c3, r1c0, r1c1, ...]

按行处理（thread t → 行 t 的第 col 列）：相邻线程访问相邻地址 → 合并 ✅
按列处理（thread t → 第 t 行的列）：相邻线程访问相隔一行的地址 → 不合并 ❌
```

这个"行列陷阱"在**矩阵转置**里体现得最典型，下一节实战验证。

## 6. 实战案例：矩阵转置的"合并访问陷阱"

任务：把 `N×N` 矩阵转置，`out[j][i] = in[i][j]`。

### 6.1 两种写法，一种快一种慢

```cuda
// 写法 A：读合并，写不合并
// 每个线程读一行里的连续元素（合并 ✅），写回转置位置时是列方向（不合并 ❌）
int i = blockIdx.y * blockDim.y + threadIdx.y;   // 行
int j = blockIdx.x * blockDim.x + threadIdx.x;   // 列
out[j][i] = in[i][j];   // 按行读入 → 合并；按列写出 → 不合并

// 写法 B：把数据经共享内存转一道，两边都合并 ✅✅
// 1) 连续读进共享内存（合并） 2) 从共享内存转置读出（合并）
__shared__ float tile[TILE][TILE+1];   // +1 是 padding，防 bank conflict
```

**为什么写法 A 总有一边不合并**：一个 warp 的 32 个线程，`threadIdx.x` 连续 → 读 `in[i][j]` 时 `j` 连续 → 读合并；但写 `out[j][i]` 时是**行下标**连续 → 跨行写 → 写不合并。读写总有一头吃亏。

### 6.2 用共享内存"转个弯"，两头都合并

```
1. 全体线程连续读 in 的一小块（合并 ✅）→ 存进共享内存 tile
2. __syncthreads()
3. 从 tile 里按转置后的顺序连续写 out（合并 ✅）
```

共享内存充当"转置中转站"，把"不合并"的读写挡在高速的共享内存一侧。这就是 `code/03_memory/` 里的练习，也是很多高性能 kernel 的通用套路：**用共享内存把访存模式"捋直"**。

> 💡 小结：合并访问不只靠"写对下标"，还常需要**配合共享内存**来改变数据的流动方向。先看懂 6.1，再跑一遍 6.2，合并访问这个概念就扎实了。

## 7. 内存速查表 & 性能检查清单

### 7.1 内存速查表

| 内存 | 声明/分配 | 作用域 | 速度 | 容量 | 关键注意 |
|---|---|---|---|---|---|
| 寄存器 | 局部变量 | 线程私有 | ~1 周期 | 每线程几十个 | 用得多会挤掉 occupancy |
| 本地内存 | 溢出的局部变量 | 线程私有 | 慢（实为全局内存） | — | 尽量避免 |
| 共享内存 | `__shared__` | block 内共享 | ~20 周期 | 最多 ~48 KB/block | 要同步、防 bank conflict |
| 全局内存 | `cudaMalloc` | 所有线程 | ~200-400 周期 | 几 GB~几十 GB | **必须合并访问** |
| 常量内存 | `__constant__` | 所有线程只读 | 同地址广播快 | 64 KB | 各线程访问不同地址会变慢 |
| 纹理/表面 | API 绑定 | 所有线程只读 | 有纹理缓存 | 任意 | 图像类局部性好时用 |

### 7.2 写完一个 kernel 自问 5 句

1. **全局内存访问合并了吗？** `threadIdx.x` 连续 ↔ 地址连续？没有 → 立刻改
2. **数据有反复复用吗？** 有 → 搬进共享内存，别反复读显存
3. **共享内存够不够？** 超出 48 KB 每 block 了？要动态申请或减小 tile
4. **写共享内存后 `__syncthreads()` 了吗？** 没同步就读写 → 数据竞争
5. **寄存器用太多了吗？** 编译看 `-Xptxas -v`，超 128 个要小心 occupancy

> 内存部分到这儿打住。下面进入性能优化——§7 速查表里被点名两次的 **occupancy（占用率）** 和 **bandwidth（带宽）**，正是下一半的两个主角。

## 8. 占用率（Occupancy）：把"等人"变成"换人"

### 8.1 回顾：GPU 靠"换人"隐藏延迟

02_cuda_basics.md §3.2 讲过，GPU 的线程等数据时（全局内存 ~200-400 周期），调度器**立刻换下一个 warp 去算**——这叫延迟隐藏。它的前提是：**SM 上得有足够多待命的 warp**。驻留的 warp 越多，越能填满这段等待时间。

**占用率（occupancy）** = 实际驻留在 SM 上的 warp 数 ÷ SM 能容纳的最大 warp 数。

```
例：一个 SM 最多能驻留 64 个 warp（GTX 1080 的极限是 64）
  当前 kernel 只驻留 32 个 → occupancy = 50%

occupancy 低 → 等待数据时没 warp 可换 → 计算单元空转 → 变慢
```

> 一句话：**占用率衡量的是"SM 上有多少活等着干"**。它是性能的"地基"——但注意，占用率高 ≠ 一定快（见 §9），它只是必要条件。

### 8.2 四个决定占用率的"墙"

SM 能驻留多少 warp，受四个资源限制，谁先到顶谁就是瓶颈（**取最小值**）：

| 限制来源 | GTX 1080（Pascal）参考 | 计算方法 |
|---|---|---|
| 每 SM 最大线程数 | 2048 线程 | `2048 ÷ block_size` 得最多 block 数 |
| 每 SM 最大 block 数 | 32 | 直接数 block |
| **寄存器** | 每 SM 65536 个 | `65536 ÷ (每线程寄存器数 × block_size)` |
| **共享内存** | 每 SM 96 KB（默认块内上限 48 KB） | `96KB ÷ (每 block 共享内存)` |

```
例子：block_size = 256，每线程用 32 寄存器，每 block 用 8 KB 共享内存

  线程墙：2048 / 256         = 8 个 block
  块数墙：32                  = 32 个 block
  寄存器墙：65536 / (32×256)  = 8 个 block  ← 卡这里
  共享内存墙：96 / 8          = 12 个 block

实际驻留 = min(8, 32, 8, 12) = 8 个 block = 2048 线程 = 100% occupancy
```

> ⚠️ 关键结论：**每线程用太多寄存器、或每 block 用太多共享内存，都会"堵死"驻留数**。这就是本篇 §2/§3 提到的权衡：寄存器/共享内存给得越多，单线程越"舒服"，但能同时干活的人越少。

### 8.3 占用率与 block 大小的关系

- block 太小（如 64 线程）：block 数墙先到顶，驻留线程数上不去
- block 太大（如 1024）：调度不够灵活，且受 2048 线程墙限制只能放 2 个
- **经验值**：128/256 通常是甜点；warp 是 32 线程，block 取 32 的倍数避免尾部空 warp

> 实测：Nsight Compute 里直接读 `Achieved Occupancy` 这个指标，不必手算。手算是为了**理解瓶颈在哪面墙**。

## 9. 两个吞吐：算力 vs 带宽，谁是瓶颈？

### 9.1 GPU 是"内存墙"机器

GPU 有两张"吞吐能力"的牌：

```
算力吞吐：每秒能算多少次浮点运算（TFLOPS）
内存吞吐：每秒能从显存搬多少字节（GB/s）

一个 kernel 能跑多快 ≈ min( 受算力限制, 受带宽限制 )
```

| | 算力（GTX 1080 参考） | 带宽（GTX 1080 参考） |
|---|---|---|
| FP32 | ~8.9 TFLOPS | — |
| 显存带宽 | — | ~320 GB/s |

**把问题反过来算**：如果一个内核每读 1 字节要做 8 次浮点运算（算术强度 = 8 FLOP/byte），那么 320 GB/s 的带宽能支撑 8.9 TFLOPS 吗？

```
320 GB/s × 8 FLOP/byte = 2560 GFLOPs = 2.56 TFLOPS < 8.9 TFLOPS
→ 内存先把算力"饿死"了 → 这类内核是"带宽受限"（memory-bound）
```

### 9.2 算术强度（Arithmetic Intensity）：判断受限类型的钥匙

> 这个概念在 00_why_gpu.md §11 首次出现，这里是它的实战用法。

```
算术强度 = 一次内核总共的浮点运算数 ÷ 一次内核从全局内存搬的字节数
          （FLOP/byte）

- 算术强度高 → 数据搬进来能算很久 → 容易吃满算力 → compute-bound
- 算术强度低 → 数据刚搬进来就算完了 → 卡在带宽上 → memory-bound
```

| 典型内核 | 算术强度 | 瓶颈类型 |
|---|---|---|
| 向量加法 `c[i]=a[i]+b[i]` | ~0.33 FLOP/byte | 严重 memory-bound |
| softmax / LayerNorm | 低 | memory-bound |
| 矩阵乘法（tiling 后） | 随 tile 增大而升高 | 接近 compute-bound |
| 卷积（大 channel） | 高 | compute-bound |

**优化方向完全不同**：
- **memory-bound**（向量加、attention、量化后的 LLM 解码）：优化重点是**减少字节数**——合并访问、用 FP16/int8 减数据量、多算子融合
- **compute-bound**（GEMM 大矩阵）：优化重点是**提高计算效率**——tiling、寄存器复用、用 Tensor Core

> 💡 记住这张图，它是整个性能优化的"总开关"：**先判断自己是 memory-bound 还是 compute-bound，再决定往哪使劲**。

## 10. 实战一：矩阵乘法 naive → tiling 的完整动机

### 10.1 目标：手写 SGEMM（单精度矩阵乘）

`C[M][N] = A[M][K] × B[K][N]`，每个输出元素 `C[i][j]` 需要读 A 的一行 K 个、B 的一列 K 个：

```cuda
// naive 版：每个线程算一个输出元素
__global__ void sgemm_naive(const float* A, const float* B, float* C,
                            int M, int N, int K) {
    int row = blockIdx.y * blockDim.y + threadIdx.y;   // 输出行 i
    int col = blockIdx.x * blockDim.x + threadIdx.x;   // 输出列 j
    float sum = 0.f;
    for (int k = 0; k < K; k++)
        sum += A[row * K + k] * B[k * N + col];        // 每个 k 读两次全局内存
    C[row * N + col] = sum;
}
```

**它为什么慢？** 数一下访问量（假设 M=N=K=1024）：

```
每个线程算 1 个输出：
  读 A：K 次     读 B：K 次     共 2K 次全局访问
全部线程：M×N 个输出 × 2K 次 = 2×1024×1024×1024 ≈ 2.1G 次浮点运算
对应全局内存读取：每个 A[i][k] 被读 N 次、每个 B[k][j] 被读 M 次！

算术强度 ≈ 2 FLOP ÷ (2×4 字节) ≈ 0.25 FLOP/byte → 严重 memory-bound
```

**核心问题：数据复用为零**。A 的一行明明可以反复用，naive 版却每次都重新从显存读。

### 10.2 优化第一步：tiling（分块）→ 用共享内存做复用

思路：既然相邻线程算的输出会**共用同一块 A 的子矩阵、同一块 B 的子矩阵**，那就把这些子矩阵**先整体搬进共享内存**，再慢慢用。

```
把输出 C 分成 BLOCK×BLOCK 的小块（tile），每块交给一个 block：

  一个 block 负责 C 的一个 BLOCK×BLOCK 小块：
  1. 循环 K/BLOCK_TILE 次：
      把 A 的一个 BLOCK×BLOCK_TILE 小块拷进共享内存 As（合并访问）
      把 B 的一个 BLOCK_TILE×BLOCK 小块拷进共享内存 Bs（合并访问）
      __syncthreads()
      块内线程从 As/Bs 里算累加（读共享内存，快）
      __syncthreads()
  2. 写回 C 的小块

全局内存访问量从 O(N³) 降到 O(N³ / BLOCK)：
  例：BLOCK=16 → 全局读减少 16 倍；BLOCK=32 → 减少 32 倍
```

**这是本篇 §3.2 的落地实现**，代码在 `code/04_optimization/`（`sgemm_naive.cu → sgemm_shared.cu`）。

### 10.3 优化第二步：register tiling —— 每个线程算多个输出

共享内存版每个线程只算 1 个输出，读写共享内存也要花周期。更进一步：**让每个线程算 2×2 或 4×4 个输出**，把 As/Bs 的元素读到**寄存器**后重复用 4 次，进一步降低共享内存带宽压力：

```
每线程算 2×2 个输出：
  读 As 一个元素 → 可参与 2 个输出的累加（寄存器复用）
  读 Bs 一个元素 → 可参与 2 个输出的累加
  共享内存访问量再减半，同时寄存器里的中间结果被反复用
```

### 10.4 三版对比（期望趋势，数值以 Nsight 实测为准）

| 版本 | 全局读次数（1024³） | 瓶颈类型 | 相对速度 |
|---|---|---|---|
| naive | ~2.1G | memory-bound（0.25 FLOP/byte） | 1× |
| shared tiling (32×32) | ~67M | 过渡 | ~5-10× |
| tiling + register (4×4) | ~67M | 逼近 compute-bound | ~15-20× |
| 调参后（Tensor Core/cuBLAS） | — | compute-bound | 30×+（cuBLAS 才是终点） |

> 提醒：**手写 SGEMM 永远跑不过 cuBLAS**——cuBLAS 还叠加了寄存器分块、双缓冲、按 K 展开、甚至 Tensor Core。手写的价值是**理解优化每一招为什么有效**，最终 PyTorch 调 cuBLAS 时才看得懂它的报告。

## 11. 实战二：tiling 里的两个隐藏坑

### 11.1 bank conflict：共享内存 tile 的行长

本篇 §3.4 说过，共享内存一次一个 warp 只能访问 32 个不同的 bank。tiling 后，一个 warp 的 32 个线程往往同时读 `As[threadIdx.y][k]`（同一行的不同列）——**行下标相同 → 列地址连续 → bank 恰好错开，通常没事**。

真正要注意的是**行长必须是 32 的倍数时会撞 bank**：

```cuda
// 行长 = 32（恰好是 bank 数）→ 线程读同一行时全部命中同一列 bank
__shared__ float As[32][32];
float v = As[ty][tx];          // tx 连续 → bank = tx，ok
float w = As[ty + 1][tx];      // 行距 32 → 和上一行同一 bank → 潜在冲突

// 修复：padding 一列，把行错开
__shared__ float As[32][32 + 1];   // 行长 33，非 32 倍数，天然错开 bank
```

### 11.2 `__syncthreads()` 放错位置 = 结果错误

共享内存版的核心纪律：

```
拷入 As/Bs → __syncthreads() → 计算读 As/Bs → __syncthreads() → 进入下一轮
```

漏掉任何一个同步点，都可能让线程 B 读到还没被线程 A 写好的数据。同步点放对，结果才对。

## 12. 更高层视角：把优化分成四板斧

| 招数 | 解决的问题 | 对应本篇 |
|---|---|---|
| **合并访问** | 带宽浪费 | §5 |
| **共享内存复用（tiling）** | 全局内存读太多次 | §10.2 |
| **寄存器复用（register tiling）** | 共享内存带宽也用满 | §10.3 |
| **占用率调优** | 延迟藏不住 | §8 |

这四招层层递进：先让每次搬运"不浪费"（合并），再让搬运次数"变少"（tiling），最后让算力"吃满"（register tiling + occupancy）。**FlashAttention 也是这套逻辑**（05_llm_acceleration.md 会看到同样的 tiling 思路）。

## 13. 用 Nsight Compute 分析：让数字说话

### 13.1 工具链

| 工具 | 干什么 | 何时用 |
|---|---|---|
| `ncu`（Nsight Compute） | **逐 kernel 性能分析**：占用率、吞吐、stall 原因 | 优化每个 kernel |
| `nsys`（Nsight Systems） | 全局时间线：kernel 启动、memcpy、空隙 | 找"整体瓶颈在哪" |
| `nvidia-smi` | GPU 利用率、显存占用（粗粒度） | 快速扫一眼 |

> 远端 Win10 已装 **Nsight Compute 2022.1.1**（见 01_environment.md），与 CUDA 11.6 配套，可直接 `ncu`。

### 13.2 基本用法

```bash
# 用 nsys 看整体：哪个 kernel 最耗时、有没有 memcpy 空隙
nsys profile ./sgemm

# 用 ncu 分析单个 kernel 的关键指标
ncu --set full ./sgemm

# 只看最关心的几个指标（快很多）
ncu --metrics sm__throughput.avg.pct_of_peak_sustained_elapsed, \
    gpu__compute_memory_throughput.avg.pct_of_peak_sustained_elapsed, \
    sm__warps_active.avg.pct_of_peak_sustained_active ./sgemm
```

### 13.3 五个必看的指标

| 指标 | 含义 | 判断 |
|---|---|---|
| `Achieved Occupancy` | 实际占用率 | 太低（<50%）→ 查寄存器/共享内存墙 |
| `SM [%]` | 计算单元利用率 | 接近 100% → 已 compute-bound |
| `Memory [%]` | 内存系统利用率 | 接近 100% 且 SM 低 → memory-bound |
| `DRAM Throughput` | 显存带宽用了多少 | 瓶颈判断的核心 |
| `Warp Stall 原因` | 每个 warp 在等什么 | 等内存 → memory-bound；等 barrier → 同步问题 |

```
看懂组合：
  SM 高 + Memory 低 → 计算密集，还能优化算法本身
  SM 低 + Memory 高 → 带宽受限，省字节才有效（§9 的判断落地）
  SM 低 + Memory 低 → 占用率太低 / 同步太密 / 启动开销大
```

### 13.4 一个分析例子：naive SGEMM

```
$ ncu ./sgemm_naive
Achieved Occupancy : 100%          ← 占用率没问题
SM Throughput      : ~10%          ← 计算单元几乎闲着
DRAM Throughput    : ~95%          ← 显存带宽被拉满

结论：memory-bound 确诊。占用率已经很高，继续堆线程没用，
     必须减少全局读次数 → 上 tiling。这就是 §10 方案的数据依据。
```

### 13.5 分析 sgemm_shared 后的预期变化

```
SM Throughput   : ~10% → ~40%
DRAM Throughput : ~95% → ~40%
→ 瓶颈从"带宽"转向"计算"，此时再上 register tiling / Tensor Core 才有效
```

> 这个"瓶颈转移"的过程就是优化：**每一步都先把当前最紧的瓶颈解开，再让下一个瓶颈暴露出来**。

## 14. 调优迭代流程（作业方法论）

```
1. 先跑通（结果正确）
2. ncu 看指标 → 判断 memory-bound 还是 compute-bound（§13.3）
3. 针对瓶颈选招（§12）
4. 改完再测：关注目标指标有没有变（而不是只看 wall time）
5. 重复，直到收益递减
```

**注意事项**：
- 对比必须**同一次程序里跑所有版本**，排除启动/驱动抖动
- 用 `cudaEvent` 计时（01_environment.md 有写法），不要用 CPU 墙钟直接量 kernel
- 每个优化单独 commit，方便回退和对照（本仓库学习闭环的 commit 规范）
